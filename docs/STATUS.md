## 7. WO-RENDER-01 — PART B·C **종결** (2026-08-17)

직전 판은 PART C 를 "부분 — 자동배포 경로 미해결" 로 남겼다. **이번에 닫았고, 닫는 과정에서
같은 틈이 하나 더 있었다는 것을 발견했다.**

### 무엇이 열려 있었나 — 두 겹

**틈 1: 페이로드.** `rebake-payload` 잡이 `vercel-production-deploy.yml`(트리거 `workflow_dispatch`
하나뿐) 안에만 있었다. 그런데 Vercel Git 자동배포가 살아 있어 `main` push 마다 배포가 나간다.
→ 재생성은 **수동 실행 배포에만** 붙고 평상시 머지 경로에는 안 붙었다.

**틈 2: 프론트 별칭.** `verify-production.ts` 를 붙인 첫 실측에서 곧바로 걸렸다.
백엔드 정규 도메인은 **프로젝트 도메인으로 등록돼 있어** Vercel 이 자동 할당한다.
프론트 정규 도메인은 **그냥 별칭**이라 `alias set` 스텝이 붙여줘야 한다.
→ **Git 자동배포는 프론트 별칭을 옮기지 않았다.** 머지 직후 실측:

```
프론트 최신 프로덕션 배포   READY · 커밋 4653190f · 별칭 0개
프론트 정규 도메인          1시간 반 전 빌드 (dpl_A3gJeVqx…, 15:03Z)
buildId                     정규 bd2mmusvXRD45Bco6elhc ≠ 최신 hTFMwPFrh0rn8vZBGJTwG
```

**#1076 과 같은 사고가 구조적으로 재발하고 있었다.** 페이로드만 보고 PART C 를 닫았다면 놓쳤다.

### 처리

`rebake-on-git-deploy.yml`(`push: [main]`) 3잡:

| 잡 | 하는 일 |
|---|---|
| `align-web-alias` | Vercel API 로 **이 커밋 SHA 와 일치하는 READY 프로덕션 배포**를 찾아 정규 도메인에 붙이고 확인. 못 찾으면 실패(엉뚱한 빌드 금지) |
| `rebake` | 버전 라우트를 폴링해 **정규 도메인이 이 커밋을 서빙할 때까지 기다린 뒤** 페이로드 재생성 |
| `verify` | `if: always()`. `verify-production.ts` 를 그대로 호출 — 검증 규칙을 복제하지 않는다 |

> **왜 배포를 기다리는가**: `push` 는 Vercel 빌드보다 먼저 발동한다. 그대로 굽면 **옛 코드가
> 페이로드를 만들고 `asOf` 만 새로워진다** — 검증은 통과하고 화면은 틀린, 가장 나쁜 위장된 통과다.

Deploy Hook(방향이 반대) · Vercel 웹훅→`repository_dispatch`(설정이 레포에 안 남고 PAT 을
Vercel 에 보관해야 한다) 대신 `push` 를 골랐다 — 전부 레포 안에 있고 이력이 Actions 에 남는다.

### 실측 검증 — "배선했다" 로 끝내지 않았다

| 머지 | 결과 |
|---|---|
| `4653190` (#1103) | 자동 트리거 → 배포 대기 2분 → 재생성 `published=10 ledgerAppended=1 ms=21571` → **verify exit 0** |
| `9197fbe` (#1104) | `Success! fomo-web-… now points to fomo-pqe2w2dcc-…` → 프론트 서빙 커밋 `9197fbe7` 확인 → 재생성 200 → **verify exit 0 (4/4 통과)** |

### 12-5. 처방 — 여섯 갈래

12-3 의 복구는 사람이 `gh run rerun` 을 친 것이고, 그것은 처방이 아니다. 같은 사고가 다시
일어날 때 **사람 없이도 화면이 안 비는지**가 기준이다. 네 갈래로 나눠 고쳤다.

#### (1) 발행 가드 — 검증을 쓰기 **앞으로** 옮겼다

`apps/web/lib/quiet-pick.ts` `quietPickPublishBlockReason()` 이 `writeFeedContent` **직전에**
판정한다. 차단 시 아무것도 쓰지 않고 직전 페이로드를 그대로 남긴 채 `503` + `blocked` 사유를
돌려준다. 차단 조건 셋:

| 조건 | 판단 근거 |
|---|---|
| 필수 입력 실패 (`QUIET_PICK_REQUIRED_INPUTS`) | 신호가 없는 게 아니라 신호를 **읽지 못한** 것이다 |
| `picks: 0` | 빈 덱은 어떤 이유로도 발행하지 않는다 |
| 직전 대비 절반 미만 (직전 4장 이상일 때) | 0장은 아니지만 반쪽 덱이 조용히 나가는 경로를 막는다 |

절반이라는 하한은 실측으로 골랐다 — `docs/audit/deck_stagnation_raw.json` 의 14일
(2026-08-05~18) `published` 는 **매일 10장**으로 상한에 붙어 있었고 한 번도 흔들리지 않았다.
정상 운영에서 반토막은 관측된 적이 없으므로 이 하한이 평상 회전을 오판할 위험은 사실상 없다.

종전 검증은 워크플로의 **쓴 뒤** 스텝에 있었다. 그래서 잡은 붉게 표시됐지만 사용자는 이미
빈 덱을 봤다 — 검증이 쓰기보다 늦으면 그것은 가드가 아니라 사후 보고다. 하루 묵은 덱은
`asOf` 로 정직하게 표시되지만, 빈 덱은 AGENTS.md 자동 실패 목록에 오른 회귀다.

**화면 쪽은 이미 정합하다.** 가드가 차단하면 사용자는 직전 페이로드를 본다 — 그것이 정직하려면
"언제 기준인지" 를 밝혀야 하고, 그 표면은 이미 있다: `apps/fomo-web/lib/deckStale.ts`
`staleLabel()` 이 1시간 넘은 페이로드에 `N시간 전 기준`·`N일 전 기준` 을 붙이고
`DeckTitle` 이 `data-testid="deck-stale"` 로 그린다(DS-02 §9). 즉 **가드는 메커니즘,
스테일 라벨은 고백**이고 둘이 짝이다 — 새 UI 를 만들 필요가 없다. 만약 스테일 라벨이 없었다면
이 가드는 "묵은 덱을 새 덱인 척 보여주는" 다른 종류의 거짓말을 만들었을 것이다.

`prior` 읽기도 `readFeedContentStrict` 로 바꿨다. 삼킨 `null` 은 "아직 안 구웠다" 와
"DB 읽기가 실패했다" 를 같게 만들고, 후자라면 붕괴 기준선이 조용히 0 이 되어 가드가 무력해진다.

#### (2) fail-open 을 이름으로 남긴다

`readSupplyDemandHistoryByTickersStrict` 를 새로 두고(`supply-demand-store.ts`) 픽 엔진이
그것을 쓴다. 종전 fail-open 은 store **안**에 있었으므로 엔진의 `.catch()` 는 애초에
발동하지 않았다 — 그래서 사고 당시 `qualification` 이 평범한 0 으로 보였다.

`buildQuietPickResponse` 의 `guardedInput()` 이 실패를 **삼키면서 이름을 남긴다** →
`qualification.inputFailures`. 계속 삼키는 것은 맞다(소스 하나 죽었다고 덱 전체를 못 굽는 것은
과잉이다). 문제는 삼킨 흔적이 없어 가드가 판단할 근거가 없었다는 점이다. 이 배열이 비어 있으면
진짜 조용한 날이고, 이름이 있으면 장애다. `feed-content-store.readFeedContentStrict` 와 같은 규약.

#### (3) 커넥션 풀 — 재생성이 물러났다 재시도한다

세 후보 중 **재시도/백오프**를 택했다.

| 후보 | 판정 |
|---|---|
| `pool_size` 인상 | ✗ 레포 밖이다 — Supabase/Vercel 설정(`PRISMA_CONNECTION_LIMIT`). 사람이 해야 한다. **미해결로 남는다** |
| 프리웜·재생성 직렬화 (공유 concurrency group) | ✗ GitHub Actions 는 그룹당 대기 실행을 하나만 큐에 두고 앞선 대기분을 **취소**한다. `us-market-prewarm` 은 5분마다 돌아서 프리웜 슬롯이 조용히 유실된다 — 고치려는 것보다 나쁜 새 실패 모드 |
| 재생성 백오프 재시도 | ✓ 전부 레포 안. 사고 당시 실패는 **일시적이었고**(사람이 재실행하니 그대로 10장) 그 회복을 사람 손 없이 쓴다 |

두 워크플로(`vercel-production-deploy.yml` · `rebake-on-git-deploy.yml`)의 재생성 스텝이
`0 → 45 → 90 → 150초` 백오프로 최대 4회 시도한다. 백오프 폭은 프리웜 슬롯(5분 간격)을 넘긴다.
`401/403` 은 즉시 멈춘다(재시도해도 같다).

**재시도가 안전한 이유는 (1) 때문이다** — 라우트가 쓰기 전에 판정하므로 실패한 시도는 페이로드를
건드리지 않는다. 같은 날 원장 중복은 #1081 의 selection 존재 검사가 막는다.

#### (4) 문서만 바뀐 배포는 재생성하지 않는다

**방아쇠가 문서 커밋 하나였다.** 재생성이 만들 차이가 0 인 배포였고, 위험만 있었다.

- `vercel-production-deploy.yml`: 새 `rebake-scope` 잡이 **정규 도메인이 지금 서빙하는 커밋**부터
  배포 대상까지의 변경 경로를 본다. 전부 `docs/`·`*.md` 면 `rebake-payload` 를 건너뛴다.
- `rebake-on-git-deploy.yml`: `github.event.before`..`github.sha` 로 같은 판정. 트리거의
  `paths-ignore` 로 막지 **않는다** — 그러면 `align-web-alias` 까지 안 돌고 프론트 정규 도메인이
  직전 배포에 남아 `verify-production.ts` 가 `뒤처짐` → **fail** 로 판정한다. 별칭은 모든 push
  에서 옮겨야 하고, 건너뛸 것은 재생성뿐이다.

둘 다 **판정 불가면 재생성한다**(서빙 커밋을 못 읽음·force-push·계보 끊김). 모를 때는 굽는 쪽이
안전하다. 문서 + 코드 혼합 커밋은 정상적으로 재생성한다.

#### (5) 잡 실패가 무엇을 뜻하는지 구분한다

12-4 가 드러낸 구멍이다. 종전 검증 스텝은 되읽기가 실패하면 `재생성 직후인데 페이로드가 NaN분
전 것이다. 화면에 닿지 않았다` 를 냈다 — **읽지 못한 것을 닿지 않았다고 말했다.** 2차 발생에서
페이로드는 정상 10장이었는데 그 문구가 나왔다. 대응이 정반대인 두 상황에 같은 말을 하면
사람은 매번 처음부터 조사해야 한다.

검증 스텝을 셋으로 갈랐다. 되읽기도 재시도한다(재생성만 재시도하고 되읽기는 한 번만 읽던 것이
2차 거짓 실패의 직접 원인이다).

| 결과 | 판정 | 문구 |
|---|---|---|
| 읽었고 신선하다 | **통과** | — |
| 읽었고 묵었다 | **실패** | 화면에 닿지 않았다 (진짜 그 상황이다) |
| 재시도 후에도 못 읽었다 | **미확인** | 페이로드 상태를 확인하지 못했다 — 재생성 응답은 `ok:true` 였다 |

세 번째는 `AGENTS.md` 의 종료코드 규약(`2` = 미확인, **통과가 아니다**)과 같은 정신이다.
못 쟀다는 말과 괜찮다는 말은 다르고, 못 쟀다는 말과 틀렸다는 말도 다르다.

#### (6) 게이트가 빈 덱을 통과시키지 못하게 한다

`scripts/verify-production.ts` 에 **실패조건 ④ `picks: 0`** 을 넣었다(종전 셋 → 넷).
12-4b 에서 이 검사가 없어 36분을 놓쳤다.

`watching` 은 세지 않는다 — 지켜보는 중 선반은 픽이 아니고, 그것만 있는 화면은 사용자에게
여전히 "오늘은 없다" 다. 읽지 못한 경우는 `fail` 이 아니라 `미확인` 으로 남긴다(종료코드 2).

이것으로 층이 셋 다 덮인다: **엔진**이 빈 덱을 쓰지 않고((1)), **워크플로**가 실패의 뜻을
구분하고((5)), **게이트**가 빈 덱을 통과시키지 않는다((6)). 셋 중 하나만 있어도 이번 세 번은
막혔겠지만, 세 번 다 다른 층에서 새어 나왔다.

### 12-5c. 처방 (4)가 만든 충돌 — 그리고 첫 문서 push 에서 걸렸다 (14:42 UTC)

§12-5b 를 기록한 **문서 커밋을 올리자 `rebake-on-git-deploy` 가 실패했다.** 재생성 판정은
정확했다 — `판정: false — 문서만 바뀐 push`. 실패한 것은 뒤이은 `verify` 잡이다.

```
❌ 페이로드 asOf ≥ 마지막 배포 시각
   asOf 2026-08-24T14:39:36.427Z 가 배포 2026-08-24T14:42:14.129Z 보다 3분 이르다
```

**두 규칙이 정면으로 부딪쳤다.**

| 규칙 | 말하는 것 |
|---|---|
| §12-5 (4) | 문서만 바뀐 배포는 **재생성하지 않는다** |
| `verify` 실패조건 ② | 페이로드 `asOf` 는 **마지막 배포 시각 이상**이어야 한다 |

문서 커밋을 올리면 배포 시각만 새로워지고 `asOf` 는 그대로다 → ② 가 **매번 거짓 실패**를 낸다.
`paths-ignore` 를 쓰지 않은 이유(§12-5 (4))와 같은 종류의 상호작용인데, 이쪽은 미리 못 봤고
**실물 push 에서 잡혔다.**

#### 틀린 쪽은 대리 지표였다

② 가 잡으려던 것은 "새 코드가 옛 페이로드를 서빙한다" 이고, **마지막 배포 시각**은 그 대리
지표였을 뿐이다. (4) 가 "배포 ≠ 페이로드 변경" 을 만들면서 대리가 깨졌다. 재야 할 것은
**"배포가 있었나" 가 아니라 "페이로드를 바꿀 변경이 있었나"** 다.

`verify-production.ts` 의 ② 를 **`docs/`·`*.md` 를 제외한 최신 커밋 시각**과 재도록 바꿨다.
문서만 바뀐 배포는 이 값이 안 움직이므로 조용하고, 코드가 바뀌면 즉시 움직인다.
코드 커밋 시각을 못 구하면(shallow clone) `fail` 이 아니라 **미확인**으로 남긴다 —
문서 배포에서 거짓 실패를 내느니 못 쟀다고 말하는 쪽이 낫다.

```
고친 뒤 — exit 0
✅ 페이로드 asOf ≥ 최신 코드 커밋 — asOf 가 최신 코드 커밋보다 3분 늦다
   (마지막 배포보다는 3분 이르지만 그 배포는 문서 변경뿐 — 재생성 생략이 맞다)
```

> 같은 실패 로그에 `❌ 정규 도메인 커밋 … → behind` 도 함께 떴는데 **그것은 일시적이었다** —
> 문서 커밋의 백엔드 자동배포가 아직 별칭에 닿기 전이었고, 2분 뒤 재실행하니 `same` 이었다.
> 한 판정에 진짜 실패와 타이밍 실패가 섞여 있었다.

### 12-6. 남는 문제 — 사람 필요

| 문제 | 왜 레포에서 못 고치나 |
|---|---|
| **DB 커넥션 풀 15** | Supabase Supavisor 세션 모드 `pool_size` 와 Vercel 환경변수 `PRISMA_CONNECTION_LIMIT` 는 대시보드 설정이다. 12-5 (3) 의 재시도는 **증상을 견디는 것**이고 원인은 그대로 남아 있다 — 프리웜 3종과 재생성이 겹치면 여전히 마른다 |

회귀 테스트: `apps/web/__tests__/lib/quiet-pick-publish-guard.test.ts`
(`EMAXCONNSESSION` 재현 포함 11케이스).

> **문서 커밋 하나 배포하려고 전체 배포를 돌린 것이 방아쇠였다.** 재생성은 문서 변경과 무관한데도
> 같은 워크플로에 묶여 있어 매번 함께 돈다 — 코드가 안 바뀐 배포에서 재생성을 건너뛸 수 있어야 한다.

## 13. 카드·상세 지적 대응 — 근거·14%·제각각 (2026-08-25)

광혁이 실 화면 3장을 놓고 세 가지를 지적했다: **근거가 없다 · 카드 UI 가 제각각이다 ·
14% 가 뭐냐.** 셋 다 코드에서 확인됐고 셋 다 서로 다른 결함이었다.

### 13-1. 「14%」 — 앱이 자기 기준을 두 개 갖고 있었다

`volumePct`(매수량 ÷ 20일 평균 거래량 × 100)에 임계가 **둘**이었다.

| | 상수 | 값 | 14.4% 를 어떻게 다루나 |
|---|---|---|---|
| 카드 | `RATIO_PCT` | 10 | 52px 히어로 숫자 |
| 상세 | `VOLUME_SHARE_FLOOR` | 20 | **행을 안 만듦** (주석: "20 미만은 소음") |

풍산 14.4% 가 정확히 그 사이였다 — **카드에서 화면에서 가장 큰 것이 상세에서는 존재하지
않았다.** 확인하러 들어간 자리에서 확인 대상이 사라진다.

`RATIO_PCT` 를 **20 으로 올려 통일**했다. 08-22 관측 공백(2.5~22.7) 안이라 그때 분류는
하나도 안 바뀐다. 그리고 `depthSections.ts` 가 숫자를 복사하지 않고 `RATIO_PCT` 를
**import** 하게 해서 다시 갈릴 수 없게 했다. 근거는 `docs/audit/WO-HOOK-01_THRESHOLDS.md` §2-1.

덧: 10~25% 를 전부 `상당 부분을 사갔어요` 로 부르던 갈래를 지웠다 — 그건 후킹이 아니라
말을 안 한 것이다. 하한이 20 이 된 지금 전 구간이 구체적 분수를 말한다(절반 / 3분의 1 / 5분의 1).

### 13-2. 「근거가 없다」 — 상세가 카드보다 증거가 적었다

A형 카드는 「주가 / 외국인 매수 누적」 두 선의 갭을 보여준다. 그 갭을 보고 상세로 들어가면
**회색 주가선 하나만** 있었다 — `DepthChart` 가 종가선과 무효선만 그렸기 때문이다.

규칙으로 고정한다: **상세는 카드보다 증거가 적으면 안 된다.** 상세 「근거」가 `CardFigure` 를
**그대로 재사용**한다(형별 분기를 복제하지 않는다 — 복제하면 언젠가 갈린다). 260일 차트는
그대로 두되 역할을 나눈다: 위는 **증거**(갭·비중·연속), 아래는 **맥락**(눌린 정도·되돌아보는 선).

> 한 그림에 합치는 안을 먼저 시도했다 — 실패했다. 신호 창이 3일이면 누적선이 260일 차트
> 오른쪽 끝 몇 픽셀에 뭉개져 아무것도 증명하지 못한다. 실측으로 확인하고 접었다.

### 13-3. 「왜 지금 사는가」에 반대 증거가 앉아 있었다

실측(한글과컴퓨터): `이력 · 비슷한 신호 79번 중 37번 올랐어요 (47%)`.
**동전 던지기보다 낮은 값이 "사는 이유" 자리에 있었다.** `buildWhyNowRows` 가 `n > 0` 이면
승률을 무조건 찍었다. `WHY_NOW_MIN_WIN_RATE = 50` 하한을 뒀다.

숨기는 것이 아니다 — 성적은 상세의 `이런 패턴` 행이 승률과 무관하게 그대로 보여준다.
여기서 빼는 것은 **이 질문의 답이 아니기 때문**이다.

### 13-4. 「제각각」 — 3형은 의도지만 공통 문법이 없었다

3형(A 역행 / B 비율 / C 희소성)은 WO-HOOK-01 설계다. 블록 순서(①~⑥)도 이미 공통이었다.
갈라져 있던 것은 **④ 그림 안**이다.

| | 종전 | 지금 |
|---|---|---|
| accent 가 가리키는 것 | A 매수 누적선 · C 매수 연속 구간 · **B 비율이라는 계측값** | 셋 다 **매수** |
| 그림 아래 한 줄 | A 범례 · C 캡션 · **B 없음** | 셋 다 mono 캡션 |

규칙 둘을 세웠다. **① accent 는 언제나 "돈이 들어온 것"이다.** 형마다 뜻이 바뀌면 스와이프할
때마다 색을 다시 배워야 한다. **② 그림 아래 한 줄이 accent 를 설명한다.**

B형을 52px 맨몸 숫자 → **하루 거래량 중 매수분 막대**(`RatioBar`)로 바꿨다. 종전 숫자는
카드 상단 `+5.7%` 바로 아래 라임색으로 놓여 **수익률로 읽혔다** — 둘 다 퍼센트라 눈이 같은
종류로 묶는다. 막대는 accent 를 다시 매수분으로 되돌리고 캡션이 무엇의 몫인지 말한다.

카드 본문 자체에는 이제 accent 가 **한 번도** 없다 — 세 형 모두 자기 그림 컴포넌트가 하나씩 갖는다.

### 13-5. 남는 것

풍산처럼 `volumePct` 가 10~20 인 픽은 이제 B형이 못 되고, 다른 형 재료가 없으면 **덱에서
빠진다**(광혁 지시: "14%는 후킹멘트가 아니야. 저 카드는 제외해"). 덱 장수가 그만큼 줄 수 있다 —
§12-6 의 장수 하향 추세와 겹치면 **가드가 아니라 엔진**을 봐야 한다.

### 13-6. 재지적 대응 — 마스킹 회귀와 "제자리" 거짓말 (2026-08-25)

#### (1) 앞단 카드에 종목명이 보였다

실측: 덱 첫 카드에 `한글과컴퓨터 030520`. **내가 어긴 게 아니라 WO-HOOK-01 §2-3 이
"상세를 열면 그 카드는 영구 해제" 로 정해둔 동작**이었다 — 한 번 열어본 종목이라 이름이 나왔다.
그 규칙 자체가 마스킹 장치를 무력화하므로 **폐기한다.** 덱 앞면은 해제 상태와 무관하게 항상
가린다(`cardRevealed = false`). 해제 기록은 남긴다 — 상세 화면이 쓰고, 되돌릴 때 한 줄만 고친다.

#### (2) "주가는 제자리인데" 인데 차트가 요동쳤다

**훅이 판정하는 창과 그리는 창이 달랐다.**

| | 창 | 근거 |
|---|---|---|
| 훅 | 신호 기간 **3~6일** | `priceChangeSincePct`(신호 시작가 대비) |
| 그림 | **40일** | `min(priceSeries, cumulativeBuySeries)` 전부 |

결과가 이랬다. 셋 다 틀렸다:

| 종목 | 지금 훅 | 그린 40일 구간 | 실제로 맞는 말 |
|---|---|---|---|
| 한글과컴퓨터 | 제자리 | +4.1% · 진폭 27.8% | **빠지는데** |
| 휴니드 | 빠지는데 | **+4.0%** (오히려 상승) | **제자리** |
| 퍼스텍 | 빠지는데 | −1.9% · 진폭 **40.4%** | 빠지는데 |

모듈 문서는 이미 `A 역행 | 매수 누적 시계열 + **같은 기간** 주가` 라고 적어뒀는데 코드가 그걸
안 지켰다. **훅을 그린 창으로 판정하게** 하고 창을 `DIVERGENCE_WINDOW = 12` 로 고정했다.
12는 실측으로 골랐다(근거표는 `card-type.ts` 상수 주석 — 40 / 12 / days×3 / 10 비교, 표본 3장).

#### (3) 차트가 1% 움직임도 산맥처럼 그렸다

(2)만 고쳐서는 부족하다. `normalize` 가 min→0 · max→1 로 늘리므로 **진폭이 작아도 화면은
요동친다** — 문장이 맞아도 그림이 과장하면 여전히 거짓말로 읽힌다. 주가선에
`normalizePrice` 를 둬서 진폭이 기준(20%) 미만이면 세로를 덜 쓰고 가운데로 모은다.
누적선은 형태만 읽으므로 예외다.

#### 배포 전 시뮬레이션 (실데이터 3장)

```
한글과컴퓨터  제자리(40일) → 빠지는데(12일 · −7.6% · 진폭 11.6%)  차트 높이 58%
휴니드        빠지는데(40일) → 제자리(12일 · +0.1% · 진폭  8.0%)  차트 높이 40%
퍼스텍        빠지는데(40일) → 빠지는데(12일 · −6.3% · 진폭 15.0%)  차트 높이 75%
```

휴니드가 이 수정의 요점을 보여준다 — **"제자리" 라고 말하면서 차트도 실제로 40% 높이만
쓴다.** 종전에는 "빠지는데" 라고 말하면서 선은 올라가고 있었다.

### 13-7. 배포 직후 pool 고갈 4차 — 이번엔 **조회 경로**였다 (2026-08-24 23:57~00:01 UTC)

§13-6 배포 확인 중 정규 도메인 덱이 `잠시 후 다시 열어주세요` 를 띄웠다.

```
GET /api/fomo/quiet-picks → HTTP 503 (5회 연속)
  Error querying the database: FATAL: (EMAXCONNSESSION)
  max clients reached in session mode - max clients are limited to pool_size: 15
```

**§12 와 성격이 다르다. 구분이 중요하다.**

| | §12 (1~3차) | 이번 (4차) |
|---|---|---|
| 무엇이 실패했나 | **쓰기** — 빈 페이로드를 발행 | **읽기** — 페이로드는 정상(picks 8) |
| 발행 가드가 막나 | ✅ 막는다 | **해당 없음** — 쓰기 경로가 아니다 |
| 사용자 화면 | 빈 덱 | `잠시 후 다시 열어주세요` |
| 회복 | 재생성 필요 | **약 2분 뒤 자동** |

즉 §12 의 처방 6갈래는 이 경우를 다루지 않는다. 그것들은 전부 **발행** 경로의 방어이고,
이번엔 **조회** 경로가 마른 것이다. 빈 덱보다는 낫지만(정직한 오류 표시) 사용자는 여전히 못 본다.

방아쇠는 배포였을 가능성이 크다 — `rebake-payload` 가 DB 를 크게 쓰고 그 직후 조회가 몰렸다.

> **네 번째다.** §12-6 에 "네 번째가 없을 이유가 아직 없다" 고 적어둔 그대로 났다.
> `pool_size 15` 는 여전히 레포 밖(Supabase Supavisor · Vercel `PRISMA_CONNECTION_LIMIT`)이고,
> 이제 **쓰기뿐 아니라 조회도** 마른다는 것이 확인됐다. 조회 경로에 스테일 서빙 폴백이
> 있는지 점검할 가치가 있다(`staleServe` 규약은 이미 있다 — 이 라우트가 쓰는지 미확인).

## 14. WO-RESET-01 — 화면 줄이기 + 잘못된 것 고치기 (2026-08-25)

남기는 화면은 둘이다: **카드 한 장, 그리고 그걸 누르면 나오는 상세.**

### 14-A. 없앤 화면 — 데이터는 그대로, 화면만

| | 무엇을 뺐나 | 남긴 것 |
|---|---|---|
| A-1 | 「지켜보는 중」 선반 | `WatchShelf` 컴포넌트·페이로드 `watching` 필드 |
| A-2 | 「성적표」 탭 진입 | `/track-record` 라우트·API·원장 적재 |
| A-3 | 「내 기록」 탭 + 관심 등록(★) | `MyRecordTab`·`watchlist` 모듈 |
| A-4 | 하단 탭 바 · 검색 버튼 | `SearchOverlay` 컴포넌트 |

「지켜보는 중」이 하던 말은 **우리 내부 규칙 설명**이었다 — `같은 종류 신호가 오늘 덱에 이미
찼어요` 를 사용자가 알 이유가 없다. 성적표의 `채점 대기 8건` · `판단 440건` 도 같다.

`about` 페이지의 성적표 링크도 끊었다 — 면책 모달에서 `about` 으로 갈 수 있어 2홉이면
도달했다. 기록이 계속 쌓인다는 문장 자체는 사실이라 남겼다.

### 14-B. 고친 버그 넷

#### B-1. 전 종목 `0.0%` — 장전에 구운 껍데기였다

```
정규 도메인 실측: KR 7장 전부 changePct = 0 (US Angel Studios 만 −1.37 로 정상)
asOf 2026-08-24T23:57Z = 08:57 KST — 장 시작 3분 전
같은 날 23:39 KST(장 마감 후) 구운 페이로드는 +0.7% 로 정상이었다
```

장전에는 네이버가 등락률 `0.00%` 껍데기를 준다. 그 0 이 페이로드에 굳어 하루 종일 박힌다.
**이미 알려진 것이다** — `feed-briefing.ts` 의 `krPublishBlockReason` 이 `PREOPEN` 을 같은
근거로 차단한다(2026-07-14 실측). 그 가드가 브리핑에만 있고 픽에는 없었다.

거들던 것이 하나 더 있다: `front.signals.changePct ?? rowChangePct ?? hint` 에서
**`0 ?? x` 는 0** 이므로 앞 소스의 껍데기가 뒤 소스의 실값을 가로막았다.

`usableChangePct()` 로 **0 이 아닌 첫 값**을 고르고, 다 0 이면 `undefined` 를 준다.
프론트에도 `displayChangePct()` 를 뒀다 — 페이로드는 하루에 한 번 구워지므로 고친 코드가
배포돼도 그날 구 페이로드는 여전히 0 을 들고 있다. **진짜 보합인 날도 함께 가려진다.**
그 손실은 받아들인다 — `0.0%` 는 아무것도 알려주지 않고 껍데기와 구별할 방법도 없다.

#### B-2. 「역행」 카드가 역행이 아니었다

지적: *"주가는 빠지는데 기관은 사고 있어요" 라는데 회색선과 라임선이 거의 나란히 움직인다.*

**둘 중 무엇인지 쟀다 — 후자였다.** 정규화 탓이 아니라 실제로 역행이 아니었다.
(정규화는 선형변환이라 상관계수를 바꾸지 않는다. 즉 이 수치가 화면 모양 그대로다.)

| 종목 | 상관계수 | 훅 |
|---|---|---|
| **한글과컴퓨터** | **+0.81** | 빠지는데 ← 지적받은 그 카드 |
| **셀바스AI** | **+0.56** | 빠지는데 |
| 퍼스텍 | +0.06 | 빠지는데 |
| 풍산 | −0.02 | 제자리 |
| 휴니드 | −0.29 | 제자리 |

종전 A형 조건은 `change <= QUIET_UP_PCT` — **주가 한 계열만** 보는 조건이라 매수선이
어떻게 가든 통과했다. 역행은 두 선의 **관계**인데 관계를 재지 않았다.

`DIVERGENCE_MAX_CORRELATION = 0.5` 를 넣었다. "절반 이상 함께 움직이면 역행이라 부르지
않는다." 미달이면 A 를 건너뛰고 B·C 가 이어서 판정한다.

> 부수 효과: **단조 상승 주가는 이제 A형이 될 수 없다.** 누적 매수선도 단조 증가라
> 상관이 0.87 까지 올라간다. 그것이 맞다 — 주가가 매수와 나란히 오르면 역행이 아니다.
> 실제 주가는 흔들리므로(지그재그 상관 0.17) 정상 픽은 통과한다.

#### B-3. 회사 설명이 등기부였다

`REGISTRY_SENTENCE` 가 `목적사업` 은 잡는데 `목적으로 설립` 은 안 잡아 그대로 통과했다.
`HISTORY_SENTENCE`(설립·상장·계열회사·인수·보고서 기준일·본점)를 추가해 **문장째 버린다**
— 단어를 오려내면 조사가 남고 뜻이 깨진다. 다 버려서 남는 게 없으면 화면은
`substance`(무엇을 파는가 한 줄)로 채운다. 실측에서 한글과컴퓨터가 그 경로로
「오피스SW 및 솔루션 개발·판매」가 됐다.

#### B-4. 상세에 차트가 둘이었다

역행 차트만 남기고 260거래일 차트를 없앴다. 되돌아보는 선(점선)은 역행 차트로 옮겼고,
주가선과 **같은 축**에 얹기 위해 무효선도 주가 정규화를 함께 거친다.
쓰이지 않게 된 `DepthChart` 는 통째로 지웠다 — 데드 코드를 남기면 다음 사람이 되살린다.

### 14-C. 완료 확인 (로컬 실앱, 375px)

> 통과했다. 손대지 않았지만 **알고 넘어간다**(대기를 조건 기반으로 바꾸는 것이 정석).

## 15. WO-RESET-02 — 「왜 사는지」 근거 만들기 (2026-08-25)

「왜 지금 사는가」가 회사 **상태** 두 줄이었다. `이익이 나고 있어요` — 그래서? 이익 나는
회사는 널렸다. **사건이 없고 날짜가 없었다.** 이제 날짜와 사건이다.

### 15-A. 공시 수집 (PART A)

| | 내용 |
|---|---|
| 무엇 | 종목별 최근 90일 — 날짜 · 제목 · 종류 · 링크. **본문은 저장하지 않는다** |
| 어디서 | KR `opendart.fss.or.kr/api/list.json` · US `data.sec.gov/submissions` |
| 언제 | `disclosure-collect.yml` 08:40 KST(픽 재생성보다 **먼저**) |
| 어떻게 | 크론 라우트 `cron/disclosures` |

**라우트인 이유**: `DART_API_KEY` 가 GitHub 시크릿에 없고 Vercel 환경변수에만 있다(실측
2026-08-03). 워크플로에서 직접 부르면 키가 빈 값이라 **조용히 0건**을 모은다. `holding-probe`
와 같은 방식이다.

**증분이다.** 매 실행이 90일을 다시 훑지 않는다 — 기본 5일치를 받아 기존 저장분과 합치고
90일 밖을 떨군다. 첫 채움은 `?days=90`. 시간 예산을 넘기면 거기까지 저장하고
`truncated: true` 를 남긴다 — **부분 수집을 완전 수집으로 착각하면 "공시가 없다" 가 거짓말이
된다.** 그 문구가 §C-4 의 핵심이므로 `truncated` 면 그 말을 하지 않는다.

빈 수집으로 기존 저장분을 덮지 않는다(§12 의 교훈) — 0종목인데 직전에 데이터가 있었으면
그건 새 사실이 아니라 장애다.

**분류**(A-2)는 순수 함수다(`disclosure-kind.ts`). 규칙으로 하고 **모르겠으면 `기타`**.
`투자판단 관련 주요경영사항` 은 무엇이든 될 수 있으므로 기타다. SEC 는 제목이 없어 **폼 번호**
로 분류한다(`10-Q`→실적, `4`→지분). `8-K` 는 무엇이든 담아서 기타다.

### 15-B. 실적 (PART B)

**전환만 본다.** `이익이 나고 있어요` 는 근거가 아니고 `7월 28일에 2분기 영업이익이 흑자로
돌아섰어요` 는 근거다 — 날짜와 변화가 있다. 계속 흑자·계속 적자는 `null` 이다.

날짜는 그 분기의 **공시일**(`filed_at`)이다. 기간말로 대신하지 않는다 — `6월 30일에 흑자
전환했어요` 는 그날 발표된 것이 아니라서 시점이 거짓이 된다.

새 수집이 없다. 팩트시트 파이프라인이 이미 굽는 `fiscal.quarters` 를 **읽기만** 한다.

### 15-C. 타임라인 (PART C·D)

```
왜 지금 사는가
8월 11일   단일판매·공급계약체결 · 계약금액 320억   [원문]
8월 14일   그 다음부터 임원이 사기 시작했어요
이 시점에 함께 있었던 일들이에요. 왜 샀는지는 저희도 확인할 수 없어요.
```

**날짜 항목이 하나도 없으면 섹션을 통째로 안 그린다**(§C-3). `지금 PBR 0.36배` 만 있는 것은
근거가 아니라 답하는 시늉이다. 매수 시작일이 항상 있으므로 실제로는 바닥이 보장된다.

값·가격은 **특이할 때만**(§C-2 4·5번) — 밴드 상·하위 20%, 52주 저점/고점 15% 이내.
`저점에서 16% 위` 같은 애매한 위치를 넣던 것이 근거를 밍밍하게 만들었다.

**섹션 다섯 개**(PART D): 왜사는가 → 무슨회사 → 얼마나샀나 → 값 → 틀리면.
「근거」를 「얼마나 샀나」로 바꿔 「무슨 회사」 뒤로 내렸다 — 근거를 대는 자리는 이제 맨 위다.
「우리 기록」은 목록에 없어 화면에서 뺐다(컴포넌트·원장은 남는다).

### 15-D. 아직 안 된 것

**공시 수집이 아직 한 번도 안 돌았다.** 라우트·워크플로·저장소는 배포됐지만 실데이터가
없으므로 지금 타임라인에는 **매수 시작일 한 줄만** 나온다. 첫 채움(`?days=90`)을 돌린 뒤에야
공시 줄이 붙는다. 「날짜 항목 0개 비율」 보고도 그 뒤에 의미가 생긴다.

## 16. WO-RESET-03 — 카드 종류 늘리기 (진행 중, 2026-08-26)

카드가 하루 8장이고 거의 다 국내였다. **신호가 한 종류뿐이라서다** — 누가 사고 있다.
컨셉(`뉴스 나오기 전에 돈이 먼저 들어간 곳`)은 그대로 두고, 그 흔적을 **가격·거래량**에서도 찾는다.

### 16-A. PART B 순서 중 1·2번 완료

WO 가 "앞의 것이 끝나야 다음으로 간다" 고 못박았다. 새 수집이 필요 없는 둘을 먼저 했다.

| 형 | 카드 | 조건 | 그림 |
|---|---|---|---|
| **D** | 시장은 빠지는데 이것만 버티고 있어요 | 지수 대비 **일별** 초과가 5일 연속 + 창 안 지수 하락일 ≥2 + 창 전체 지수 하락 | 지수선(회색) vs 종목선(라임) |
| **E** | 석 달 만에 처음 거래가 N배로 늘었어요 | 60거래일 평균의 3배 이상 + **가격 변동 ≤3%** | 거래량 막대(급증만 라임) |

**일별로 비교한다** — 누적으로만 보면 첫날 한 번 크게 오른 뒤 계속 밀린 종목도 "계속 강하다"
가 된다. **지수 하락일을 요구한다** — 없으면 지수가 오른 구간에서 조금 더 오른 종목까지
`시장은 빠지는데` 가 되어 문장이 거짓이 된다.

E형의 `가격 변동 ≤3%` 가 이 카드의 존재 이유다. 거래가 붙었는데 **가격이 이미 뛰었으면**
조용한 신호가 아니라 이미 일어난 뉴스다. 우리가 찾는 것은 그 전이다.

### 16-B. 규칙

- **카드에 종류 라벨을 붙이지 않는다**(D-1). `CardType` 의 `D`·`E` 는 구성·텔레메트리가 쓰는
  내부 이름이고 화면에 나가지 않는다. e2e 가 카드 본문에 라벨이 없음을 고정한다.
- **모든 종류에 그림이 있다**(D-4). 그림을 못 만들면 카드를 만들지 않는다 — 두 형 모두
  재료가 모자라면 `null` 을 돌려주고 그 테스트가 있다.
- **덱 15장**(E-1), **한 종류가 절반을 넘지 못한다**(E-3 — `MAX_SAME_KIND_RATIO` 0.6→0.5).
  종전 0.6 은 종류가 사실상 하나이던 시절 값이라 무의미했다.

### 16-C. 배관에서 지킨 것

일봉은 프리웜 캐시에서 **한 쿼리로** 읽는다(`readKrCandleCacheMany`). 66종목을 `Promise.all`
로 읽으면 커넥션 풀에서 66슬롯을 잡고, 그것이 §12 의 사고였다. 지수도 종목마다 받지 않고
코스피·코스닥 두 번만 받는다.

D형 범례의 **회색선 이름**을 넘길 수 있게 했다 — 안 넘기면 `주가 / 이 종목` 이 되어 둘 다
주가로 읽힌다(프리뷰 실측에서 잡았다). 지금은 `코스피 / 이 종목` 이다.

### 16-D. 아직 안 한 것

| 순서 | 카드 | 상태 |
|---|---|---|
| 3 | 자사주 매입 (A-2) | **미착수** — RESET-02 공시에서 `주주환원` 을 고르면 되므로 거의 공짜다 |
| 4 | 지분 5% (A-3) | **미착수** — 같은 공시에서 `지분` |
| 5 | 공매도 축소 (A-4) | **미착수** — KRX·FINRA 새 소스 필요 |
| 6 | 실적 갭 (A-5) | **미착수** — 컨센서스 필요(없으면 전년 대비 대체) |

| 무엇이 걸러내나 | 시총·거래대금이 아니라 **목록에 없으면 아예 안 본다** |

이 목록의 원래 목적은 스캔 대상이 아니었다. 파일 주석이 그렇게 적어뒀다 —
*"종목 인식 어휘(보수적)… 오인식 1건이 신뢰를 깨므로 별칭은 좁게"*.
**뉴스 원문에서 종목명을 찾는 사전**이지 유니버스가 아니다. 그것을 유니버스로 쓰면서 66에 갇혔다.

#### 확대 경로는 이미 열려 있다

`fetchKrMarketRows` 가 네이버 시세를 **시장당 10페이지**씩 긁는다(`PAGES_PER_MARKET = 10`,
KOSPI+KOSDAQ). 즉 **수백 종목의 시세·거래대금·시총이 이미 들어오고 있다.**
`krDefs` 를 `STOCK_VOCAB` 이 아니라 그 행들로 만들면 유니버스가 바로 늘어난다.

**다만 공짜가 아니다** — 확대 전에 확인해야 할 것:
- 일봉 프리웜(`kr-candle-prewarm`)이 유니버스만큼 돈다. 300종목이면 프리웜도 300회
- `identity`(회사 정체 한 줄)·별칭이 사전 밖 종목엔 없다 → 카드 품질 게이트가 어떻게 되는지 미지수
- 발견 API 응답 시간(완료 확인 13)

### 17-B. 임계 확정 — 감이 아니라 분포로 (완료 확인 1·2)

배포 후 조건을 **걸지 않고** 잰 분포가 근거다(56종목).

| | 실측 | 종전 | 지금 |
|---|---|---|---|
| D 최대 연속일수 | **3일** (4일↑ **0종목**) | 5일 | **3일** |
| E 거래량 배수 | 최대 **53.8배** (2배↑ 8종목) | 3배 | 3배 (유지) |

**D형**: 5일 연속 매일 지수를 이기는 종목은 실제로 없다. 3으로 낮춘다.

**E형**: 배수는 넉넉했는데 카드가 0장이었다 — 전부 **가격 조건**에서 걸렸다. 당연하다,
거래가 53배 터진 날 가격이 3% 안에 머물 리 없다. 창을 바꾼다:

```
전   급증 **당일** 가격 변동 ≤ 3%
후   급증 시작 직전 → 오늘 **순변동** ≤ 5%
```

이 카드가 말하려는 것은 "거래는 붙기 시작했는데 **아직** 안 움직였다" 이고, 그건 하루가
아니라 급증 이후 지금까지의 이야기다. 급증일에 튀었다가 되돌아왔으면 여전히 "아직 안
움직인" 것이 맞다(테스트로 고정).

> **5%는 잠정값이다.** WO 가 준 범위(3~7%)의 가운데다. 같은 배포에 순변동 분포 계수기
> (`spikeNetUnder3/5/7`)를 넣었고, 그 숫자가 모이면 확정한다. **감으로 정한 값을 남기지 않는다.**

### 17-B2. E형 상한 **7% 확정** (완료 확인 2)

창을 바꾼 코드를 먼저 배포하고, **조건을 걸지 않은 채** 순변동 분포를 쟀다
(거래량 2배 이상 8종목, 2026-08-26 프로덕션):

| 순변동 | 종목 |
|---|---|
| ≤ 3% | **0** |
| ≤ 5% | **0** |
| ≤ 7% | **2** |

WO 가 준 범위는 3~7%. **그 안에서 카드가 하나라도 나오는 값은 7% 뿐이다.** 잠정 5% → 7% 확정.
범위를 넘겨 늘리지 않는다. 더 필요하면 조건을 푸는 게 아니라 유니버스를 넓힌다(17-D).

### 17-C. D형이 왜 아직 0장인가 — 계수기를 나눴다

첫 실측이 이상했다: 연속 3일 이상이 **4종목**인데 카드는 **0장**. D형 게이트는 셋이다 —
① 연속일수 ≥3 ② 창 안 지수 하락일 ≥2 ③ 창 전체 지수 변동 < 0. 지금 계수기는 ①만 센다.
**어디서 죽는지 감으로 답하지 않기 위해** ②·③ 통과 수를 따로 센다
(`streak3AndIndexDown` · `streak3AndIndexFell`). 다음 배포에서 답이 나온다.

### 17-D. 유니버스 확대 — 66 → **326** (WO PART D)

진단(17-A)이 말한 그대로 고쳤다. **`STOCK_VOCAB` 은 손대지 않는다** — 그건 뉴스 인식 사전이고,
넓히면 오인식이 생긴다. 픽 엔진에 **자기 유니버스**를 준다(`apps/web/lib/pick-universe.ts`).

```
                  종전    지금
픽 엔진 유니버스    66  →   326   (KOSPI 158 · KOSDAQ 168)
  사전에 있던 것    66  →    66   (하나도 안 버림)
  새로 들어온 것     0  →   260
```

| 결정 | 왜 |
|---|---|
| 시장별 150씩 자른다 | 시총 순위는 **시장 안에서만** 비교된다. 섞어 자르면 코스피가 거의 다 먹고, 정작 "아직 조용한" 종목이 많은 코스닥이 사라진다 |
| 컷 밖 사전 종목도 남긴다 | 확대했는데 나오던 카드가 사라지면 개선이 아니다 (그래서 300이 아니라 326) |
| 사전 밖 종목은 별칭 = 정식명 하나 | 이 정의는 **스캔용**이지 뉴스 인식용이 아니다. 어휘를 넓히지 않는다 |
| 새 시총 컷을 만들지 않는다 | 감으로 정한 임계를 남기지 않는다. 이미 알려진 대형주는 **실측 게이트**가 이미 거른다 — `mega_cap`(시총 순위 ≤100) · `turnover_top20` · `changed_15` · `illiquid` |
| 시세가 비면 사전으로 후퇴 | §12 가 그 사고였다. 유니버스 0 = 빈 덱. 후퇴하되 `krUniverseSource: "vocab"` 로 **말한다** |

#### 새로 수집할 것이 없었다

| 입력 | 이미 커버하는 범위 |
|---|---|
| 시세 행 | **1,627종목** (KOSPI 627 · KOSDAQ 1000), 279ms — 실측 |
| 일봉 캐시 | **450종목** (`kr-candle-prewarm` 의 `UNIVERSE_LIMIT`) |
| 수급 이력 | 80종목 ← **여기만 좁았다.** 같은 함수를 쓰도록 고침 |

수급 수집기(`scripts/supply-demand-collect.ts`)가 `STOCK_VOCAB` 을 훑고 있었다. 픽 엔진만
넓히고 이쪽을 두면 새 종목은 **수급 이력이 없어** 기관·외인 신호가 영원히 안 뜬다.
두 쪽이 `buildKrPickUniverse` 를 **같이** 부르므로 이제 어긋날 수 없다.

#### 유니버스 게이트는 한 곳이 아니었다 — **네 곳**이었다

`krDefs` 만 고치고 끝났다고 생각했는데 아니었다. `STOCK_VOCAB` 을 스캔 대상으로 쓰는 곳이
넷이고, 하나라도 좁으면 **카드는 나오는데 그 종목의 무언가가 통째로 빈다.**

| 곳 | 좁았을 때 생기는 일 | 지금 |
|---|---|---|
| `quiet-pick` `krDefs` | 종목을 아예 안 본다 | `buildKrPickUniverse` |
| `scripts/supply-demand-collect` | 수급 이력이 없어 **기관·외인 신호가 영원히 안 뜬다** | `buildKrPickUniverse` |
| `disclosure-collect` | 「왜 지금」의 날짜·사건 칸이 빈다 — **근거 없는 카드** | 라우트가 넘긴다 |
| `dart-disclosures` (내부자 매수) | 내부자 매수 공시를 **본 적도 없는 것**이 된다 | 픽 엔진이 넘긴다 |

넷이 같은 함수(또는 그 결과)를 보게 했고, 다시 흩어지지 않도록 테스트로 고정했다.
`signal-backtest-job` 은 그대로 뒀다 — 그건 스캔이 아니라 **채점 표본**이고, 표본을 갑자기
넓히면 지금까지의 성적과 비교가 끊긴다.

#### 미국은 이미 전체 시장을 본다

PART D 는 "US 300" 도 요구했다. 확인해보니 **확대할 것이 없다** — 미국 신호(`insider_cluster`)는
openinsider 의 *최신 클러스터 매수* 페이지에서 온다. 종목 목록으로 거르지 않는다.
`US_DISCOVERY_SYMBOLS`(98)는 시총 문맥용이지 스캔 대상이 아니다. 없는 문제를 고치지 않는다.

#### 비용 (완료 확인 13)

| | 확대 전 |
|---|---|
| 발견 API 읽기 | 0.52 · 0.67s (웜) · 3.57s (콜드) |
| 굽기(rebake) | 28.6s (`maxDuration` 300s) |

확대 후 수치는 이 배포에서 잰다. 일봉은 **한 쿼리**로 읽으므로(`readKrCandleCacheMany`)
커넥션은 늘지 않는다 — 늘어나는 것은 행 수다. 그래서 WO 가 정한 대로 **300 먼저**,
숫자를 보고 800으로 간다.

### 17-E. 확대 후 실측 — 숫자가 다 바뀌었다 (2026-08-26 배포 직후)

| | 확대 전 (66) | 확대 후 (326) |
|---|---|---|
| 유니버스 | 66 | **326** (사전 66 + 신규 260) · 출처 `market` |
| 일봉 있는 종목 | 56 | **216** |
| **D형 카드** | 0 | **1** |
| **E형 카드** | 0 | **4** |
| 연속 3일 이상 | 4 | **28** |
| 연속 **4일** 이상 | **0** | **6** |
| 거래량 2배 이상 | 8 | **26** |
| 순변동 ≤7% | 2 | **6** |

**D형·E형 카드가 처음으로 나왔다.** 카드가 안 나오던 것은 조건이 빡빡해서가 아니라
**볼 종목이 66개뿐이어서**였다. WO 가 "유니버스가 작으면 새 카드를 만들어도 장수가 안 는다"
고 한 그대로다.

#### D형 0장은 버그가 아니었다 — 계수기가 증명했다

```
연속 3일 이상          28종목
  + 창 안 지수 하락일 ≥2  →  1종목   ← 27종목이 여기서 죽는다
  + 창 전체 지수 하락      →  1종목
```

D형은 **"시장이 내리는데 이 종목만 오른다"** 이다. 그날 지수가 안 내렸으면 안 나오는 것이
맞다. 조건을 풀 이유가 없다 — 계수기를 나누지 않았으면 이걸 감으로 답할 뻔했다.

#### 비용 (완료 확인 13)

| | 확대 전 | 확대 후 |
|---|---|---|
| 발견 API 읽기 | 0.52 · 0.67s (웜) · 3.57s (콜드) | **0.47 · 0.67s (웜) · 1.14s (콜드)** |

느려지지 않았다. 일봉을 **한 쿼리**로 읽기 때문이다(`readKrCandleCacheMany`) —
커넥션은 그대로고 행 수만 늘었다. 입력 실패 0건, 덱 15장 유지.

### 17-F. 유니버스 게이트는 **다섯 곳**이었다 — 일봉 프리웜

확대 직후 진단에 `tooShort: 110` 이 찍혔다. 326종목 중 110개가 일봉 20개 미만이라는 뜻이다.
프리웜은 450종목을 덮는데 왜?

```
프리웜 450이 실제로 덮던 시장 → {"KOSPI": 450}
유니버스 326 중 프리웜 밖     → 168  ({"KOSDAQ": 165, "KOSPI": 3})
```

**450은 전부 코스피였다. 코스닥은 한 종목도 안 덮였다.** 시세 행이 KOSPI 627 → KOSDAQ 1000
순서라 앞에서 450을 자르면 코스닥에 닿지 못한다. 가격·거래량 카드(D·E형)는 일봉이 전부라
**코스닥 절반이 보이지도 않는 상태**였다.

상한을 올리지 않았다 — 프리웜의 시간 예산(50초 · 동시 8)이 이미 450에서 빠듯하다.
대신 **순서를 바꿨다**: 실제로 스캔하는 종목이 먼저다. 예산은 그대로다.

### 17-G. 프리웜 고친 뒤 실측 — 그리고 왜 **800**으로 가는가

프리웜 순서를 고치자 코스닥이 채워졌다.

| | 66 | 326 (프리웜 전) | 326 (프리웜 후) |
|---|---|---|---|
| 일봉 있는 종목 | 56 | 216 | **324 / 326** |
| 일봉 짧은 종목 | 10 | 110 | **2** |
| D형 후보 | 0 | 1 | **3** |
| 연속 3일 이상 | 4 | 28 | **48** |
| 연속 4일 이상 | 0 | 6 | **9** |
| 최대 연속일수 | 3 | 4 | **5** |
| 순변동 ≤3% | 0 | 0 | **3** |

#### 그런데 D·E형은 여전히 덱에 못 든다 — 이유가 나왔다

덱 15장은 그대로 `insider_cluster 5 · institution_streak 7 · foreign_streak 3` 이고,
`market_divergence` 는 **「지켜보는 중」에 1장**, 나머지는 그 앞에서 떨어진다.

```
탈락 사유:  mega_cap 14   ← 압도적 1위
            turnover_top20 3 · no_anomaly 2 · ran_30_since_signal 2 · …
```

원인이 분명하다. **시장별 상위 150을 보는데 "이미 알려진" 판정선이 시총 100위**
(`KR_MEGA_CAP_RANK`)다. 유니버스의 3분의 2가 그 선 안이다 — 조용한 종목을 찾겠다면서
시끄러운 구간만 훑고 있었다.

**판정선을 밀지 않는다.** 그러면 "이미 오른 종목"이 섞인다(WO 하지 말 것 2번).
대신 선 **아래**를 늘린다 — 시장별 400(총 ≈800)이면 시장별 300종목이 100위 밖에 놓인다.
WO PART D-1 이 처음부터 계획한 2차 목표가 그것이다.

프리웜도 같이 늘렸다: `maxDuration` 60→300초, 예산 50→240초, 상한 450→900.
**동시 실행 수는 안 올렸다** — 네이버를 더 세게 때리는 대신 시간을 준다
(450종목 실측 30.9초 · 실패 0 · 예산 초과 0).

#### E형 상한 7%는 **굶은 표본**에서 고른 값이다

유니버스가 66일 때는 ≤3%·≤5% 가 둘 다 0종목이라 7% 말고 선택지가 없었다. 지금은
≤3% 가 3종목, ≤5% 가 4종목이다. **표본이 바뀌었으면 임계도 다시 봐야 한다** —
800 유니버스의 분포를 보고 한 번에 정한다. 두 번 흔들지 않는다.

### 17-H. 800 배포 실측 — D·E형이 **덱에 들어왔다**, 그리고 틀린 문장을 잡았다

| | 66 | 326 | **809** |
|---|---|---|---|
| 유니버스 | 66 | 326 | **809** (사전 66 + 신규 743) |
| 일봉 있는 종목 | 56 | 324 | **799** |
| 연속 3일 이상 | 4 | 48 | **118** |
| 연속 4일 이상 | 0 | 9 | **25** |
| 최대 연속일수 | 3 | 5 | **7** |
| 순변동 ≤3% | 0 | 3 | **7** |
| **덱의 D형** | 0 | 0 | **7** |
| **덱의 E형** | 0 | 0 | **1** |

```
덱 15장:  market_divergence 7 · volume_awakening 1 ·
          insider_cluster 1 · institution_streak 4 · foreign_streak 2
```

`mega_cap` 탈락은 그대로 14다 — 판정선(시총 100위)을 **안 밀었기 때문이다.** 늘어난 것은
그 선 **아래**이고, 그 자리에서 D·E형이 처음으로 덱에 들어왔다. WO 가 금지한
"조건을 무작정 푸는 것" 없이 장수가 늘었다.

프리웜 809종목 51.4초(예산 240초) · 실패 0 · 예산 초과 0. 입력 실패 0건.

#### 그런데 상세가 **틀린 말**을 하고 있었다

덱을 열어보고 찾았다. D·E형 카드의 결론이 이랬다:

```
market_divergence | 가 조용히 4일째 매수 중 | ["거래량 평소의 39%", " 4일 연속"]
volume_awakening  | 가 조용히 1일째 매수 중 | ["거래량 평소의 45%", " 3배"]
```

세 가지가 한꺼번에 틀렸다.

| 무엇 | 왜 그랬나 |
|---|---|
| **「매수 중」** — 아무도 사고 있지 않다 | `buildQuietPickHook` 에 두 형의 분기가 없어 연속매수 템플릿으로 떨어졌다 |
| **「가」로 시작** — 주어가 없다 | `HOOK_ACTOR` 가 빈 문자열이라 조사만 남았다 |
| **「거래량 평소의 39%」**(=말라 있다) | E형 훅(`거래량 3배`)과 **정면 모순**. 매수 전제 지표를 그대로 썼다 |
| 칩 앞 공백 `" 3배"` | 빈 주체를 그대로 이어붙였다 |

카드는 멀쩡했다 — `cardType.hook`(「시장은 빠지는데 이것만 버티고 있어요」)을 먼저 보기
때문이다. **상세만** `pickHook` 을 봤다. 한 종목의 두 화면이 다른 말을 하면 어느 쪽도 못 믿는다.

고친 것: 두 형에 제 문장·제 칩을 주고, 상세도 카드와 **같은 결론**을 쓰게 했다.
숫자를 못 재면 형용사도 안 쓴다(`주가는 아직` — 「그대로」라고 단정하지 않는다).

### 17-I. 문장을 고치니 다음 문제가 보였다 — **일곱 장이 똑같았다**

훅·칩을 고치고 다시 열어보니 이렇게 나왔다:

```
market_divergence | 시장은 빠지는데 이것만 버티고 있어요 | ["4일 연속 시장 상회","코스닥 -1.7%"]
market_divergence | 시장은 빠지는데 이것만 버티고 있어요 | ["4일 연속 시장 상회","코스닥 -1.7%"]
   … 일곱 장이 글자 하나 안 틀리고 같다
```

말은 맞는데 **일곱 장이 같은 카드**다. 스와이프 덱에서 같은 문장 일곱 번은 카드가 아니라 소음이다.

원인은 둘 다 "이 종목의 숫자"를 안 쓴 것이었다.

| | 종전 | 지금 |
|---|---|---|
| 결론 | `시장은 빠지는데 / 이것만 버티고 있어요` (고정) | `코스닥는 빠지는데 / 혼자 5.2%` |
| 칩 | `코스닥 -1.7%` (같은 시장이면 전부 동일) | `코스닥보다 6.9%p 위` (종목마다 다름) |

**지어내서 다르게 만들지 않았다** — 원래 종목마다 다른 값(창 안 등락률)이 있는데 안 쓰고
있었을 뿐이다. 못 재면 종전 문장으로 돌아간다(테스트로 고정).

### 17-J. E형 상한 **3% 최종** — 굶은 표본을 바로잡는다

| 유니버스 | ≤3% | ≤5% | ≤7% | 그때 고른 값 |
|---|---|---|---|---|
| 66 | **0** | **0** | 2 | 7% (다른 선택지가 없었다) |
| 809 | **7** | 12 | 17 | **3%** |

66일 때는 3%·5%가 둘 다 0종목이라 7% 말고 고를 수가 없었다. 809로 채우니 **가장 좁은 값도
공급이 된다.** 그러면 가장 좁은 값을 쓴다 — 7%로 두면 카드가 `주가 6.3%` 칩을 달고 나가는데
(실측), 6.3% 움직인 종목을 두고 "아직 안 움직였다"고 말하는 것은 거짓이다.
**이 카드의 문장이 참이 되는 선이 임계다.**

수집 크론(거시·업종·인물·공시)은 다 걸어뒀는데 **정작 그것을 덱에 싣는 굽기가 없었다.**
모아만 두고 안 쓴 셈이다.

### 24-C. 고침

```
07:40 거시 → 08:00 업종 → 08:20 인물 → 08:40 공시 → 09:10 굽기
```

순서가 규칙의 일부다 — 수집이 끝난 **뒤에** 구워야 그날 모은 것이 그날 덱에 실린다.
테스트로 순서를 고정했다(겹치면 커넥션을 함께 잡는다).

굽기가 막히면 성공으로 넘기지 않는다 — 조용히 어제 덱이 남는 것이 가장 나쁘다.

## 23. `pool_size: 15` — **우리 코드 문제였다** (2026-08-30)

### 23-A. 아홉 번을 남 탓했다

`EMAXCONNSESSION ... max clients are limited to pool_size: 15` 이 아홉 번 났고, 그때마다
「Supabase 대시보드에서 pool 을 올려주셔야 한다」고 보고했다. **틀렸다.**

```
GitHub Actions 잡   PRISMA_CONNECTION_LIMIT=1   ← 걸려 있음
Vercel 런타임        (없음)                      ← 여기가 구멍이었다
```

`prisma.ts` 는 **환경변수가 있을 때만** 상한을 걸고 있었다. 배치 잡 워크플로 셋에는
그 변수가 있는데 **Vercel 런타임에는 없다.** 없으면 Prisma 기본값
(`물리 CPU × 2 + 1`, Vercel 에서 보통 5~9)이 쓰인다.

**람다 두셋만 동시에 떠도 15가 찬다.** 굽기 직후 되읽기가 늘 503 이던 이유가 그것이다 —
굽는 람다가 커넥션을 여러 개 쥔 채로 도는 동안 읽기 람다가 자리를 못 잡았다.

### 23-B. 서버리스는 람다당 1개면 된다

람다는 **한 번에 요청 하나**를 처리한다. 커넥션을 여러 개 들고 있어도 쓸 일이 없고,
대신 풀에서 남의 자리를 뺏는다.

| | 종전 | 지금 |
|---|---|---|
| 람다당 커넥션 | 5~9 (기본값) | **1** |
| 같은 풀(15)로 감당하는 람다 | 두셋 | **15** |
| 커넥션 대기 | 10초 뒤 실패 | **30초 대기** |

**줄 서서 기다리는 것이 즉시 실패하는 것보다 낫다.** 지금까지는 기다리지 못하고 바로 죽었다.

이미 연결 문자열에 적혀 있으면 손대지 않는다 — 운영자가 넣은 값을 코드가 덮으면 안 된다.
환경변수로도 덮을 수 있게 남겼다.

### 23-C. 교훈

**남의 설정을 의심하기 전에 우리가 그 값을 정하고 있는지부터 봤어야 했다.**
아홉 번 같은 에러를 보고도 `prisma.ts` 를 안 열어본 것이 문제였다.

## 22. WO-RESET-09 — 뉴스 (2026-08-29, 거시 완료 / 정책 보류)

### 22-A. 뉴스 소스 라이선스 — 확인 결과 (보고할 것 1번)

WO §A-2 가 정했다: **"라이선스가 불확실하면 그 소스를 안 쓴다."**

| 소스 | 판정 | 근거 |
|---|---|---|
| **FRED** (세인트루이스 연은) | ✅ **쓴다** | 공개 도메인. 키 없이 CSV. 6종 전부 200 실측 |
| 언론사 RSS (연합·한경·매경 등) | ⛔ **이번엔 안 쓴다** | 레포에 이미 붙어 있지만 제목·링크만 쓰는 조건이 각 사 약관에서 확인되지 않았다 |
| 정부 보도자료 | ⛔ **미확인** | `korea.kr` · `motie.go.kr` RSS 가 404. 공공누리 유형을 확인할 경로를 못 찾았다 |

그래서 **§A-3(거시 = 숫자)만 만들었다.** 기사에는 라이선스가 붙지만 **공공 통계 숫자에는
안 붙는다** — WO 가 그 길을 미리 짚어둔 이유가 이것이다.

```
DEXKOUS      원달러 환율    1,385.01  (08-21)
DCOILWTICO   WTI 유가       83.90     (08-25)
FEDFUNDS     미 기준금리    3.63      (07-01)
DGS10        미 국채 10년   4.67      (08-27)
SP500        S&P 500        7,711.76  (08-28)
VIXCLS       변동성 지수    14.51     (08-27)
```

### 22-B. 연결이 카드의 존재 이유다 (§B-3 · §F-3)

지표가 움직인 것만으로는 카드가 아니다. 그건 그냥 뉴스이고 **뉴스 앱과 경쟁하지 않는다.**

```
연결 <2곳  →  카드를 만들지 않는다
연결 ≥2곳  →  "우리가 최근 짚은 종목 중 N곳이 여기 닿아요"
```

마지막 줄이 전부다. 환율 숫자는 어디에나 있지만 **「우리가 짚은 종목 중 4곳」** 은
우리만 말할 수 있다.

최근 30일 픽은 스냅샷 30일치를 **한 쿼리로** 읽어 만든다 — 날짜마다 따로 읽으면
커넥션을 30개 잡고, 그것이 §12 의 사고였다.

### 22-C. 예측하지 않는다 (§F-1)

```
안 됨   환율이 오르면 이 종목이 오를 거예요
지금    환율이 오르면 수출하는 회사에 유리해요 · 이 업종은 수출 비중이 높아요
```

**회사별 수출 비중·원자재 의존도를 우리는 갖고 있지 않다.** 그래서 업종 수준의
**일반 원리**만 쓴다 — `이 업종은`이지 `이 회사는`이 아니다. 아는 것만 말한다.

업종 이름은 **네이버 산업분류 그대로** 적었다(§21 의 분류표). 임의로 만든 이름을 적으면
영영 연결이 안 된다.

### 22-D. 아무 날에나 만들지 않는다

| 조건 | 값 |
|---|---|
| 연속 방향 | **3일** 이상 |
| 누적 변동률 | 지표별 (환율 1.5% · 유가 5% · VIX 20%) **잠정** |
| 연결 종목 | **2곳** 이상 |
| 하루 최대 | **2장** |
| 위치 | 덱 **중간**(흐름 카드 뒤) — 앞쪽 3장은 종목 몫 |

지표마다 임계가 다른 이유 — 환율이 3일에 1.5% 움직이는 것과 VIX 가 1.5% 움직이는 것은
전혀 다른 사건이다. **잠정값이고** 실측 분포를 보고 확정한다.

### 22-F. 조사를 **네 번** 틀리고 나서 코드로 막았다

```
코스닥는 빠지는데            (08-27)
시장 대비이 사기 시작했어요   (08-27)
전자장비와기기으로 들어오고   (08-29)
국제 유가이 3일째 내리고      (08-30)
```

넷 다 **값을 문자열에 끼운 바로 뒤에 조사를 붙여** 생겼다. 그 값이 무엇이 될지 미리 알 수
없으므로(업종·지수·지표·사람 이름) **고정 조사는 반드시 어딘가에서 틀린다.**

매번 하나씩 고치는 대신 **코드 모양으로 막았다** — `${...}` 바로 뒤에 조사가 오면
테스트가 실패한다. 켜자마자 **16곳**이 걸렸다.

| 걸린 것 중 | 예 |
|---|---|
| 이미 틀리고 있던 것 | `워런 버핏가` (사람 이름은 받침이 섞인다) · `코스닥는` |
| 아직 안 틀렸지만 언제든 틀릴 것 | `${actor}이` · `${label}는` · `${theme}가` |

전부 `josa()` 로 바꿨다. 정규식 패턴 인자는 건너뛴다 — 거기 조사는 **출력이 아니라
원문 매칭**이라 바꾸면 오히려 안 잡힌다.

`으로` 는 **ㄹ 받침이 예외**다(`서울로` 이지 `서울으로` 가 아니다). 그 예외까지 넣었다.

### 22-E. 남은 것

| 내용 | 상태 |
|---|---|
| 거시 상세(§C) · 지표 즐겨찾기 | 미착수 — 카드의 CTA 가 아직 상세를 안 연다 |
| 정책·산업 뉴스(§A-2·§B-2) | **라이선스 확인 전까지 보류** |
| 종목 상세 2걸음에 뉴스 섞기(§D) | 위와 같은 이유로 보류 |

## 21. WO-RESET-08 — 자금 흐름 (2026-08-28, 진행 중)

### 21-A. 카드보다 **분류를 먼저 쟀다** (§E-3 · 완료 확인 9)

WO 가 못을 박았다 — *"업종 흐름 카드는 분류가 틀리면 통째로 거짓이 된다."*
그래서 만들기 전에 쟀다. 유니버스 809 기준:

| 출처 | 종목 | 비율 |
|---|---|---|
| 큐레이션 사전(`sectorOf`) | 66 | **8.2%** |
| 시세 행 업종힌트 | 0 | **0.0%** |
| **분류 없음** | 743 | **91.8%** |

**8%로는 시장 자금 흐름을 말할 수 없다.** 무분류 쪽에 삼성생명·KB금융·신한지주 같은
큰 종목이 그대로 있다.

게다가 그 8%의 라벨이 **테마**다 — `반도체 · 방산 · 2차전지 · 바이오 · AI · 원자력 · 코인`.
`코인` 은 회사의 업종이 아니다. `한화투자증권 = 코인` 사고를 만든 그 라벨이 그대로 있었다.

**이 상태로 흐름 카드를 만들면 거짓말이 된다.** 카드를 미루고 분류표를 먼저 만들었다.

### 21-B. 진짜 분류표가 있었다 — 요청 83번

네이버가 **업종 79개**와 업종별 종목 목록을 준다.

```
종목마다 조회      809번
업종에서 훑기       83번   ← 이쪽
```

이건 테마가 아니라 산업분류다 — `반도체와반도체장비` · `건강관리업체및서비스` · `은행`.
하루 한 번 갱신하고(업종은 상장·폐지 때만 바뀐다), **커버리지를 응답에 싣는다** —
그게 흐름 카드가 성립하는지의 근거다.

한 종목이 여러 업종에 나오면 **먼저 만난 업종**을 쓴다. 뒤엣것으로 덮으면 실행마다 값이
달라져 집계가 흔들린다.

### 21-C2. 흐름 카드를 덱에 이었다

분류가 96.2% 확보되자 카드를 만들 수 있게 됐다.

#### 금액을 어떻게 내나

수급 데이터는 **주식 수**로 온다. 주식 수는 종목 간 비교가 안 된다 — 삼성전자 1주와
동전주 1주가 같은 무게일 리 없다. **그날 종가를 곱해** 금액으로 바꾼다.

**추정치다** — 실제 체결가가 아니라 종가를 쓴다. 그래도 종목 간 비교를 가능하게 하는
유일한 방법이고, 업종 합계 수준에서는 방향과 크기를 보여준다. 종가를 모르는 날은
**그 행을 버린다**(지어내지 않는다).

#### 아무 날에나 만들지 않는다 (§D-2)

| 조건 | 값 |
|---|---|
| 창 | 3일 → 5일 → 20일 (짧은 것부터, 하나 나오면 멈춤) |
| 업종당 최소 종목 | **5** — 두 종목의 합계는 종목 이야기다 |
| 방향 유지 | 창의 **60%** 넘게 같은 방향 — 하루 몰빵은 흐름이 아니다 |
| 금액 임계 | 1,000억 **(잠정)** — §D-2 가 실측으로 정하라 했고, 재려면 먼저 배포해야 한다 |
| 하루 최대 | **2장** |

#### 인과로 말하지 않는다 (§E-1 · 완료 확인 7)

```
안 됨   반도체 자금이 방산으로 이동했어요
지금    반도체에서 돈이 빠지고 / 방산으로 들어오고 있어요
```

같은 돈인지 우리는 모른다. **두 사실을 나란히 말한다.** 금지어를 테스트로 막았다.

#### 덱에 섞는다 — 별도 섹션이 아니다 (§D-1)

픽 파이프라인은 종목 하나를 전제로 돈다(가격·캔들·무효선). 업종을 그 틀에 밀어 넣으면
모든 게이트에서 걸린다. 그래서 **응답에 따로 싣고 화면이 같은 덱 앞쪽에 끼워 넣는다** —
2번째와 5번째 자리다. 맨 앞은 아니다: 첫 카드는 종목이어야 이 앱이 무엇인지가 먼저 전해진다.

그림은 **막대 둘과 화살표 하나.** 산키·애니메이션 없음(테스트로 막았다).

### 21-C. 남은 것

| 내용 | 상태 |
|---|---|
| 분류 커버리지 실측 | **배포 후** — 크론이 응답에 싣는다 |
| 흐름 집계(§A-1) · 카드(§B) | ✅ (21-C2) |
| 흐름 **상세**(§C) · 업종 즐겨찾기 | 미착수 — 카드의 CTA 가 아직 상세를 안 연다 |
| ETF 자금(§A-2) · 시장 간(§A-3) | 미착수 |

**커버리지가 낮으면 카드를 만들지 않는다.** 절반의 시장으로 「시장이 이렇게 움직인다」고
말하는 것은 없는 것보다 나쁘다.

## 20. WO-RESET-07 — 유명 투자자 포트폴리오 (2026-08-27, 진행 중)

| 소스 | 주기 | 확인 |
|---|---|---|
| **ARK 일별 CSV** | **매일** | ARKK·ARKW·ARKG·ARKF 200. **티커와 CUSIP 을 둘 다** 준다 |
| SEC 13F 제출 목록 | 분기 | 버크셔 44건 조회됨 |
| SEC 13F 보유 표 | 분기 | XML 200. **CUSIP 만** 주고 티커가 없다 |
| SEC company_tickers | — | 10,388종목 |

**ARK 가 유일하게 매일 나온다** — 캐시 우드를 1순위로 잡는 이유다(WO §A-2).

### 20-B. 13F 의 진짜 문제는 티커였다

13F 보유 표는 **CUSIP 으로만** 종목을 적는다. 회사명으로 맞추면 SEC 약어
(`BANK OF AMER CORP` · `ALLY FINL INC`) 때문에 **실측 36%** 만 붙었다.

모자란 64%를 유사 매칭으로 메우지 않았다 — **오인식 한 건이 신뢰를 깬다**
(`stocks.ts` 의 오랜 규칙). 대신 셋으로 채웠다:

| 방법 | 성격 |
|---|---|
| 손으로 확인한 CUSIP 씨앗 39쌍 | **식별자다. 추측이 아니다** |
| ARK CSV 가 매일 주는 진짜 쌍 | 43쌍 이상, 매일 갱신 |
| 정규화 후 **정확히 일치**하는 회사명 | 유사 매칭 아님 |

```
버크셔 2026-Q2:  해석 36% → 100%
상위 5:  AAPL 22.0% · AXP 17.1% · KO 10.9% · GOOG 9.4% · BAC 9.2%
```

못 찾은 보유는 **버리고 센다**(`unresolved`). 카드가 몇 장 줄어드는 게 틀린 종목을
보여주는 것보다 낫다.

### 20-C. 덱에 섞는다 — 별도 탭이 아니다 (§E-1·E-2)

| 규칙 | 값 |
|---|---|
| 인물 카드 상한 | 전체의 **40%** |
| 13F 시즌(2·5·8·11월 중순) | **60%** 까지 |
| 같은 인물 연속 | **2장** |

시즌에 상한을 푸는 이유 — 분기 공시가 몰리는 날 40%로 막으면 **가장 재미있는 날에
가장 많이 버린다.** 그 시즌은 원래 그런 시즌이다.

### 20-C2. 첫 수집에서 **인물을 한 명 잘못 짚고 있었다**

크론 첫 실행 결과가 이랬다:

```
philippe-laffont(코투) → 보유 638 · 티커 미해석 322
```

코투가 638종목을 들고 있을 리 없다. SEC 등록명을 확인하니 그 CIK(`0001165408`)는
**ADAGE CAPITAL** 이었다. 코투는 `0001135730` 이다.

**누가 샀는지 틀리면 이 기능 전체가 무의미하다.** 11명 전원의 SEC 등록명을 확인해
테스트에 실측 목록으로 박았다 — CIK 는 손으로 적는 값이라 같은 실수가 또 난다.

같이 잡은 것 — 서드포인트·바우포스트가 「13F 없음」으로 실패했는데, 목록에는 멀쩡히
있었다. **없는 게 아니라 막힌 것**이었다(SEC 초당 10건 제한). 요청 간격을 넣었다.

### 20-C3. 「13F 없음」이 아니라 **XML 모양이 달랐다**

요청 간격을 넣어도 서드포인트·바우포스트가 계속 실패했다. 파일을 열어보니:

```
버크셔      <infoTable>       기본 네임스페이스
서드포인트   <ns1:infoTable>   접두 있음
```

안쪽 태그(`nameOfIssuer` 등)는 접두를 받고 있었는데 **바깥 반복만 안 받았다.**
그래서 접두를 쓰는 제출자는 보유가 0건으로 읽히고 「13F 없음」이 됐다 —
목록에는 멀쩡히 있었는데.

**「없다」와 「못 읽었다」를 또 헷갈렸다.** 이번엔 우리 파서가 원인이었다.

### 20-E. 데이터층만 만들고 **카드에 안 이었다**

광혁이 지적했다 — "머니플로우랑 인플루언서가 카드에 안 나와."

확인해보니 그대로였다:

```
quiet-pick.ts 안의 investor 언급   11회  ← 전부 덱 상한 배선이고 신호 생성이 아니다
quiet-pick.ts 안의 sectorMap       0회
QuietPickSignalKind               4종   ← 인물·흐름이 없다
```

**두 층을 만들고 카드 생성에 연결하지 않았다.** 데이터는 다 있는데 화면에 나올 길이 없었다.
이번에 이었다:

| 이은 것 | 내용 |
|---|---|
| 신호 종류 | `investor_move` 추가 |
| 검출 | 보유 두 시점 비교 → 픽 후보(노출 기간 지난 공시는 제외) |
| 카드 형 | **F형** — 보유 비중 게이지 하나 |
| 덱 상한 | `investorId` 를 후보에 실어 40%·같은 인물 2장이 실제로 걸리게 |
| 수집 크론 | 매일 08:00 분류표 · 08:20 인물 · 08:40 공시 → 그 뒤 픽 재생성 |

**같은 실수가 또 나지 않게 배선 테스트를 걸었다** — 검출기가 신호를 만들고, 그 신호가
후보에 합류하고, 카드 형이 붙고, `investorId` 가 넘어가는 네 지점을 각각 고정했다.

F형 그림은 **게이지 하나**다. 회색 = 직전까지 있던 것, 라임 = 이번에 늘어난 것,
전량 매도면 전부 회색. 사진·로고를 쓰지 않는다(§B-3).

### 20-F. 인물 카드가 0장이던 진짜 이유 — **창이 짧았다**

배선을 잇고도 0장이었다. 원인을 계수기로 갈랐다:

```
13F 11명   공시 낡음   8/14 공시 → 오늘 8/29. 노출 기간 14일을 **하루** 넘겼다
ARK        변화 없음   08-27 → 08-28 사이 20% 이상 변한 종목이 없다
```

ARK 가 진짜 문제다 — **매일 나오는 유일한 소스**인데 카드가 안 나온다.
임계를 감으로 낮추지 않고(WO-RESET-04 의 교훈) 조건 없이 분포를 쟀다:

| 일별 변화율 | 종목 |
|---|---|
| ≥2% | 2 |
| ≥5% | **0** |
| ≥20% | **0** ← 현재 임계 |
| 최대 | **4.1%** |
| 신규 편입 · 전량 매도 | **0 · 0** |

**하루 사이의 움직임은 매매가 아니라 자금 유출입이다.** ARKK 순자산이 바뀌면 전 종목
주식 수가 비례해 함께 움직인다 — 그걸 「캐시 우드가 더 샀어요」로 부르면 거짓말이다.

**임계는 틀리지 않았다.** 그 노이즈를 정확히 걸러낸다. 틀린 것은 **창**이었다 —
실제 매매는 며칠에 걸쳐 쌓이므로 하루만 보면 영영 임계를 못 넘는다.

그래서 최신과 **5일 전**을 비교한다. 창을 아직 못 채웠으면 **비교하지 않는다** —
하루 차이로 「더 샀어요」를 말하지 않는다.

#### 13F 는 분기당 14일만 나온다

이건 설계대로다(§E-3). 다만 그 창이 좁아 **비시즌에는 인물 카드가 ARK 몫**이라는 뜻이다.
WO 보고할 것 3번(13F 시즌과 비시즌의 차이)이 곧 이것이다.

### 20-D. 남은 것

| 내용 | 상태 |
|---|---|
| 카드 형(§B) · 상세 2걸음(§C-2) · 인물 페이지(§D) | **다음 조각** |
| 의회·국민연금 | 미착수 |

## 19. WO-RESET-06 — 같은 카드가 계속 나오지 않게 (2026-08-27)

### 19-A. 강등으로는 안 됐다 — **제외**로 바꾼다

천보가 계속 나왔다. 빅텍도 그랬다. WO-DECK-01 이 재노출 강등(점수 ×0.6)을 걸어뒀는데,
강등은 **순위를 낮출 뿐**이라 그 종목보다 강한 후보가 없으면 여전히 1등으로 나온다.
유니버스가 66이던 시절엔 늘 그랬다.

```
최근 3일 안에 덱에 나온 종목은 오늘 덱에서 뺀다.
```

영구 배제가 아니다 — 3일이 지나거나 **새로 생긴 일**이 있으면 다시 후보다.
빠진 종목은 「지켜보는 중」으로 사유와 함께 간다.

### 19-B. 예외 다섯 — 「연속일수가 하루 늘었다」는 예외가 아니다

| 예외 | 코드 | 상태 |
|---|---|---|
| 다른 주체 합류 | `actor_joined` | 이미 있었다 |
| 신호 종류 변경 | `structure_shift` | 이미 있었다 |
| 새 공시 | `new_material` | 이미 있었다 |
| 무효선 이탈 | `invalidation_break` | 이미 있었다 |
| **규모 급증** | `amount_surge` | **이번에 추가** |

규모 급증 임계는 **50%** 다. 진행 문구용 임계(5%)를 그대로 쓰면 누적 순매수가 매일 조금씩
늘면서 **모든 연속 신호가 매일 이 사유로 부활**하고, 그러면 3일 규칙이 있으나 마나다.
「갑자기 커졌다」고 말하려면 실제로 갑자기여야 한다.

**연속일수는 제외 판정에 아예 안 들어간다** — `recentExposure` 는 달력 날짜만 본다.
신호 속성을 하나라도 읽으면 그게 예외 통로가 되므로 테스트로 막았다.

### 19-C. 이력도 **이미 읽은 것**에서 만든다

크론이 1페이지 쿨다운 때문에 최근 8일 스냅샷을 이미 한 쿼리로 읽고 있다.
거기서 노출 이력을 만든다 — **커넥션을 더 잡지 않는다**(§12 의 교훈).

### 19-D. 다시 나온 카드는 처음 카드와 다르게 생겼다

| 요소 | 처음 | 다시 나옴 |
|---|---|---|
| 상단 라벨 | 없음 | `다시 나왔어요` (3회 이상이면 `N번째 나왔어요`) |
| 훅 | 무슨 일이 있었나 | **무엇이 새로 생겼나** (`이번엔 외국인도 사기 시작했어요`) |
| 종목명 | 가림 | **가리지 않는다** — 이미 본 종목이다 |
| 처음 가격 | 없음 | `8월 24일 처음 나왔을 때 · 2,890원 → 지금 3,035원 (+5.0%)` |

음수여도 그대로 보여준다 — 가리면 성적이 아니라 광고가 된다.

상세 1걸음에는 노출 이력이 붙는다(`이 종목, 3번째 나왔어요` + 날짜·사유·그때 가격, 최근 5회).
처음 나온 종목이면 통째로 없다.

### 19-E. 덱이 짧아지는 것은 정상이다

「적어요」 임계를 3 → **5** 로 올렸다. 0장일 때 문구도 바꿨다 —
`오늘은 조용한 곳을 찾지 못했어요` + **왜 그런지**(최근 나온 종목은 새 일이 없으면 안 넣는다).

**채우려고 규칙을 풀지 않는다.** 보충 로직이 없다는 것을 테스트로 고정했다.

### 19-F2. 배포하자마자 **내 두 규칙이 부딪혔다**

3일 규칙을 켜니 발행이 막혔다:

```
blocked: "직전 15장 → 5장 붕괴(하한 50%) — 직전 페이로드를 유지한다"
exposure: { blocked: 14 }
```

§12 의 붕괴 가드와 WO-RESET-06 §D 가 정면으로 부딪혔다.

| 규칙 | 말 |
|---|---|
| §12 붕괴 가드 | 덱이 반토막 나면 장애일 가능성이 높다 — 직전 것을 유지하라 |
| WO-RESET-06 §D | 덱이 짧아지는 건 정상이다 — 채우려고 규칙을 풀지 말라 |

가드가 잡으려던 것은 **까닭 모를 붕괴**다(입력이 조용히 실패해 반토막 나는 상황).
여기선 14장이 **왜 빠졌는지 우리가 정확히 안다** — 최근 3일 안에 나왔고 새 일이 없어서
뺐다. 규칙이 의도대로 동작한 것이지 장애가 아니다.

**가드를 끄지 않았다. 세는 대상을 바로잡았다** — 제외한 만큼을 되더해서 본다.
그러고도 반토막이면 그건 설명되지 않은 축소이므로 종전대로 막는다.
0장은 설명이 있어도 발행하지 않고, 필수 입력 실패는 설명을 보기 전에 막는다.

### 19-G. 배포 후 실측 (2026-08-27 13:20 KST)

| 보고 항목 | 값 |
|---|---|
| **덱 장수 변화** | 15장 → **5장** |
| **3일 규칙이 제외한 건수** | **14건** |
| **예외로 재노출된 건수** | **0건** (사유별 분포 비어 있음) |
| 다시 나온 카드 | 1장 (엘앤에프, 2회 — 처음 8월 19일) |

**14장이 빠져 덱이 3분의 1이 됐다.** 이게 규칙이 의도한 결과다 — 그 14종목은 최근 3일 안에
이미 나왔고 새로 생긴 일이 없었다. 채우지 않았다.

예외 재노출이 0건인 것은 **그날 아무도 조건을 못 채웠다**는 뜻이다. 예외 다섯이 헐겁지
않다는 신호이기도 하다 — 특히 규모 급증 임계를 50%로 잡은 것이 여기서 확인된다.

#### 완료 확인 11 은 **시간이 필요하다**

「3일 연속 봤을 때 같은 종목이 세 번 나오지 않는다」는 **사흘치 실제 굽기**가 있어야
확인된다. 압축할 수 없다. 지금 확인된 것은 규칙이 과거 스냅샷을 읽어 14건을 실제로
제외했다는 사실이고, 사흘 뒤 첫 카드가 매일 달랐는지는 그때 본다.

**주의** — 같은 날 여러 번 구우면 같은 종목이 다시 나온다. 3일 규칙은 **어제 이전**을 보고
오늘자 스냅샷은 입력에서 빠져 있다(자기 자신 때문에 제외되면 안 되므로). 오늘 안에서의
반복은 규칙 위반이 아니다.

### 19-F. 안 한 것 두 가지 — 이유와 함께

| WO 항목 | 왜 안 했나 |
|---|---|
| §B-2 「그림 — 새로 생긴 부분만 강조」 | **무엇이 새 부분인지 알 수 있는 계열이 없다.** `actor_joined` 면 합류한 주체의 매수 계열이어야 하는데 그건 따로 안 들고 있다. 아무 구간이나 강조하면 **거짓 표시**가 된다 — 없는 것보다 나쁘다 |
| §D 「지난 카드 보기」 | **새 화면이다.** WO-RESET-01·03 이 "새 화면(탭·섹션) 만들지 말 것" 을 두 번 못박았다. 두 지시가 충돌해 이번에는 만들지 않았다 |

§E-1 대시보드도 새 화면 대신 **배포 검증기**(`verify-production.ts`)에 붙였다 —
매 배포에서 눈에 들어오는 자리다.

## 18. WO-RESET-05 — 상세를 「읽는 흐름」으로 (2026-08-27)

### 18-A. 상세가 한 장에서 **네 걸음**이 됐다

```
1걸음  누가 쓸어담고 있나   →  얼마나 이례적인지
2걸음  왜 지금인가          →  그때 무슨 일이 있었나
3걸음  그래서 어떤 회사인가  →  좋은지 나쁜지
4걸음  계속 볼 건가         →  즐겨찾기
```

이야기 순서다 — 놀라움 → 이유 → 실체 → 결정. 한 화면에 한 걸음만 두고, 상단 진행 점이
**실제 걸음 수**를 비춘다. 데이터 없는 걸음은 목록에서 빠지므로 점도 그만큼 줄어든다.
빈 걸음을 만들지 않는다.

「틀리는 경우」를 뺐다 — `52주 저점 63,000원 이탈 여부가 다음 판단 기준이에요` 가 **모든
종목에 똑같이** 나왔고 그걸 보고 할 수 있는 게 없었다. **데이터는 그대로 두고 화면만 뺐다.**

### 18-B. 공시 제목을 사람 말로 (§3-1)

프로덕션에서 이렇게 나가고 있었다:

```
임원ㆍ주요주주특정증권등소유상황보고서
주식등의대량보유상황보고서(일반)
타인에대한담보제공결정
```

근거가 아니라 **금융감독원 서식 이름**이다. 54종 번역표를 만들었다(정본
`docs/wo/DISCLOSURE_PHRASEBOOK.md` — 코드에만 있으면 검토할 수 없다).

| 규칙 | 왜 |
|---|---|
| 번역이지 요약이 아니다 | 한 서식은 한 사건을 뜻한다. 옮기는 것은 해석이 아니다 |
| 제목에 없는 것은 안 넣는다 | 금액·평가·전망 금지. 본문을 저장하지 않으므로 재료도 없다 |
| 제목이 들고 있던 숫자는 남긴다 | `계약금액 320억` 을 떨어뜨리면 번역이 아니라 손실이다 |
| 표에 없으면 원문 그대로 | 틀린 우리말보다 원문이 정직하다 |

같이 고친 것 — **`시장 대비이 사기 시작했어요`**(33건 중 9건). 조사도 틀렸지만 더 나쁜 것은
**시장 대비도 거래량도 아무것도 사지 않는다**는 점이다. 형마다 제 동사를 쓴다.

### 18-C. 3걸음 — 숫자마다 **비교 문장** (§4)

종전 「값」은 `PER 12.25배` 하나였다. **12.25배가 싼 건지 비싼 건지 읽는 사람은 모른다.**

```
PER 12.25배    미디어 업종 중간값 18.00배보다 낮아요
               ●●●●○  미디어 업종 안에서 낮은 편이에요
```

| 결정 | 왜 |
|---|---|
| **비교 기준이 없으면 그 숫자를 안 보여준다** | 맨숫자는 아무 말도 안 한 것과 같다. 줄 자체가 사라진다 |
| 세 덩어리(돈·값·빚), **합친 점수 없음** | 합치는 순간 "이 종목 7점"이 되고 그건 추천이다 |
| `평균` 이 아니라 **중간값** | PER 은 적자 직전 종목에서 수백 배로 튀어 평균을 망가뜨린다. 화면 문구도 「중간값」이라 쓴다 |
| 부채비율은 업종 없이 판정 안 함 | 은행 1,000%와 소프트웨어 10%대를 같은 자로 재면 반드시 틀린다 |
| 적자면 PER 을 안 쓴다 | 이익이 없으면 이익 배수는 값이 아니라 잡음이다 |
| `저평가`·`유망` 금지 | `중간값 18배보다 낮아요` 는 사실, `저평가예요` 는 판단이다 |

**업종 중간값은 새로 모으는 게 없었다** — 팩트시트를 이미 전부 읽고 있고 거기 분류·PER·
PBR·부채비율이 다 들어 있다. 유니버스 때와 같다(§17-A): 데이터는 와 있었고 안 쓰고 있었다.
소속 5종목 미만이면 상위 분류로 올리고, 그래도 모자라면 업종 비교를 안 쓴다(5년 밴드로).

### 18-D. 눈으로 확인했다 (완료 확인 13)

로컬에서 네 걸음을 끝까지 걸었다 — 진행 점 이동, 걸음별 내용, 즐겨찾기 담기까지.
3걸음은 WO §4-2 모형 그대로 나온다.

### 18-D2. 성능 게이트가 잡았다 — 배럴에 넣으면 조회가 무거워진다

CI 가 막았다:

```
route:quiet-picks: 전이 모듈 130 > 예산 128
route:track-record-picks: 148 > 146
route:daily-30: 169 > 167
```

`sector-stats` · `company-read` 를 `@fomo/core` 배럴에 넣었더니, 그 배럴을 값으로 임포트하는
**조회 라우트 세 개**가 각각 +2 됐다. 이 둘은 **굽는 경로에서만** 쓰는데도 그렇다.

게이트 문구가 맞았다 — *"예산을 올리는 것은 마지막 수단이다. 먼저 왜 늘었는지 본다."*
예산을 안 올리고 **배럴에서 뺐다.** 쓰는 쪽이 경로로 직접 가져온다:

```ts
import { companyRead } from "@fomo/core/keyword-cards/company-read";
```

세 라우트 모두 원래 숫자로 돌아왔다(128 · 146 · 167). 콜드스타트가 나빠지는 것이
504 사고의 원인이었다.

### 18-E2. 배포 실측 — 번역은 됐고, **3걸음이 0종목**이었다

| 보고 항목 | 값 |
|---|---|
| **공시 번역 커버리지** | 21건 중 18건 번역 = **85.7%** (원문 그대로 3건) |
| 3걸음이 붙은 종목 | **0 / 15** |
| 업종 비교 가능 비율 | 잴 수 없음(위가 0이라) |

번역은 목표대로 동작한다. 그런데 3걸음이 통째로 비었다.

#### 원인은 §12 와 **같은 실수**였다

```
inputFailures: []          ← 아무 문제 없다고 말한다
companyRead.stocks: 0      ← 그런데 팩트시트를 한 장도 못 찾았다
```

`readAllFactSheets` 가 **스토어 안에서** `.catch(() => [])` 로 실패를 삼키고 있었다.
그러면 호출부에는 **"DB 가 죽었다" 와 "그날은 팩트시트가 없었다" 가 글자 하나 다르지
않게** 보인다. 수급 이력에서 똑같은 걸 겪고 고쳤는데(§12), 여기서 그대로 반복했다.

고친 방식도 같다 — `readAllFactSheetsStrict`(던진다)를 만들고 굽는 엔진이 그걸 쓴다.
삼키는 판은 남기되 **부르는 쪽이 고르게** 한다. 읽어온 개수도 진단에 실었다
(`qualification.factSheets`) — 0을 눈으로 볼 수 있어야 한다.

**다음 배포에서 진짜 원인이 갈린다**: `factSheets: 0` + `inputFailures` 에 이름이 있으면
장애(커넥션 풀), 이름이 없으면 정말 저장분이 없는 것이다.

### 18-F. strict 로 바꾸자 원인이 드러났다 — **장애였다**

같은 배포에서 다시 재니:

```
factSheets: 424            ← 조용히 0 이던 것
inputFailures: []
3걸음: 종목 13/15 · 업종비교 10 · 비교문장 44줄 · 점 30
```

**앞선 0은 저장분이 없어서가 아니라 그 굽기에서 DB 를 못 읽은 것**이었다. 삼키는 코드를
치우자마자 424장이 나왔다. §12 의 교훈이 왜 규칙이어야 하는지가 다시 보였다.

### 18-H. 실제 데이터를 열어보고 잡은 것 — **부채비율이 100배 틀렸다**

```
천보 → 1% | 전기제품 업종 중간값 1%보다 낮아요
```

같은 숫자를 두고 "1%보다 낮아요" 라고 말하고 있었다. 파보니 단위 문제였다 —
팩트시트의 `debt_to_equity` 는 **배수**(부채 ÷ 자기자본, `derive.ts`)인데 화면이 그대로
`%` 를 붙였다. 천보의 `1.0` 은 **1% 가 아니라 100%** 다.

**100배 틀린 숫자를 확신 있게 보여주는 것이 없는 것보다 나쁘다.** 배수 → 퍼센트로 옮기고
소수 한 자리를 남긴다(반올림하면 서로 다른 값이 같은 글자가 되어 비교가 거짓말이 된다).

### 18-I. 2걸음이 통째로 비어 있었다 — 커버리지는 **날짜만이 아니다**

부채비율을 고치고 다시 보니 이랬다:

```
whyNow 항목 18건 · 그중 공시 항목 0건
공시 저장분: 유니버스 808 인데 공시가 붙은 종목은 155
coveredFrom: 2026-05-29  ← "90일 다 봤다"
```

**유니버스를 66 → 809 로 늘렸는데 공시는 옛 66종목 것만 있었다.**

DART 목록은 하루치를 통째로 주고 **우리가 유니버스로 걸러낸다.** 그래서 유니버스가 커지면
이미 훑은 날에도 새로 걸릴 종목이 생긴다. 그런데 재개 로직은 `coveredFrom`(날짜)만 보고
*"이 날짜까지 봤다"* 며 과거를 건너뛰었다 — **새 종목의 90일 과거를 영영 안 보는 상태.**

커버리지에 **유니버스 크기**를 함께 적는다(`coveredUniverse`). 10% 넘게 커졌으면
과거 재개를 무시하고 다시 훑고, **이전 `coveredFrom` 도 물려받지 않는다** —
안 본 과거를 봤다고 적으면 「최근 90일 공시가 없었어요」가 거짓말이 된다.

잘린 수집은 유니버스 기록을 갱신하지 않는다. 부분을 완전으로 적으면 그 구간이 영영 안 채워진다.

### 17-K. 배포하고 또 열어봤다 — 조사가 틀렸다

문구 차별화는 됐다(D·E 8장 전부 서로 다른 문구, 실측). 그런데 그 문장이 이랬다:

```
코스닥는 빠지는데 혼자 18.2%     ← 「코스닥은」이 맞다
코스닥보다 7%p 위               ← 옆 카드는 7.6%p — 정밀도가 달라 보인다
```

받침 처리를 안 하고 `는` 을 그대로 붙였다. 레포에 `josa()` 헬퍼가 이미 있는데 안 썼다.
지수 이름은 `코스피`(받침 없음)·`코스닥`·`나스닥`(받침 ㄱ)이 섞이므로 고정 조사는 반드시 틀린다.

**작아 보이지만 카드 15장 중 7장에 뜨는 문장이다.** 틀린 한국어는 데이터가 틀린 것과 같은
값으로 신뢰를 깎는다. 테스트로 고정했다.
