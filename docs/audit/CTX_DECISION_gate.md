## 2. B-1 수급 주체 3분 — **수집 배선이 없다**

이 배치의 1번 목표("누가 사고 있나 — 개미·기관·외국인 전부")가 **가장 크게 막혀 있다.**

| 항목 | KR | US |
|---|---|---|
| 개인(개미) 순매수 일별 | **수집 안 됨** | 미확인 |
| 기관 순매수 일별 | 파서 있음(네이버) | 미확인 |
| 외국인 순매수 일별 | 파서 있음(네이버) | 미확인 |
| 주체별 연속일수 산출 | 타입은 있음(`streaks`) | 미확인 |
| 주체별 누적 수량·금액 | 미확인 | 미확인 |
| 소급 가능 기간 | **미확인** | 미확인 |

### 코드 실측

- `packages/fomo-core/src/supply-demand.ts` 는 **3주체를 전부 모델링**한다 —
  `foreignNet` · `institutionNet` · `individualNet`.
- 네이버 파서는 **기관·외국인 2주체만** 준다(`individualNet` 미제공, 파일 주석에 명시).
- 개인을 주는 KIS 파서(`prsn_ntby_qty`)는 **호출처가 테스트뿐이다.** 프로덕션 코드에 없다.
- `apps/web/vercel.json` 크론 10개 중 **수급 수집 크론이 없다.**

### 결론

**개인(개미) 수급은 "확보율이 낮다" 가 아니라 "수집이 돌지 않는다".**
확보율 ≥90% 조건은 지금 측정할 대상 자체가 없다 → **CTX-01 은 데이터 확장 이전에 수집 배선이 선행**이다.

기관·외국인은 파서가 있으므로 **카드에 안 보이는 것은 표출 문제**일 가능성이 크다.
다만 저장·소급 기간을 확인하지 못했다 → **미확인**.

카드 쪽 실측도 같은 결론을 지지한다(PART A): 발행 10장 중 외국인 0장·개인 0장,
`signal.actors` 는 **분해 불가능한 문자열 하나**다.

## 3. B-2 OHLCV — 조건부 GO

| 항목 | 실측 |
|---|---|
| 일봉 보관 상한 | **260거래일** (`KR_CANDLE_KEEP_DAYS = 260`, US 동일) → 250 요건 충족 설계 |
| 캐시 최소 길이 | `MIN_USEFUL_DAYS = 120` 미만은 캐시하지 않음(폴백 직접 fetch) |

| 발행 카드 실측 | 10/10 이 252~260 (min 252) |
| **유니버스 478 기준 확보율** | **미확인** |
| 거래량 결측률 | **미확인** |
| 수정주가 여부 | **부분 확인 — §3.1** |
| 분봉 | 불필요(배치 범위 밖) |

발행 카드 10/10 을 확보율로 읽으면 안 된다. 발행 게이트가 `candles < 200` 을 이미 거른다
(`cron/quiet-pick/route.ts:40`). CTX-00 실패 모드 "표본이 좋아 보임" 에 정확히 해당한다.

### 3.1 수정주가 — 전량 조정본이 아니다

`fundamentals/coverage` 의 `band_insufficient_reasons` 원문에 다음이 **실제로 집계돼 있다**:

```
  3  종가 시계열에 하루 N배 점프(N-N-N) — 분할 미조정 의심
162  종가 이력 N년 — N년 미만
 54  일별 종가 없음
156  윈도우 내 주식수 변동 N% — 기준주식수 근사 불가
```

**시스템 스스로 분할 미조정을 3건 탐지하고 있다.** 즉 "전부 수정주가" 라고 전제하면 안 된다.
동시에 **종가 이력 부족이 162건**으로 훨씬 크다 — 250거래일 확보율의 실질 병목은 여기일 가능성이 높다.

이 수치들은 펀더멘털 밴드 산출 실패 사유이지 **일봉 길이 직접 측정치가 아니다.**
직접 측정은 감사 라우트 배포 후 수행한다.

### 판정

설계상 260거래일이고 발행 카드는 전원 ≥252 이므로 **CTX-02 조건부 GO**.
단 **유니버스 확보율 미확인**이 남아 있고, 미달로 판명되면 KR/US 범위를 조정한다.

## 5. PART C 성능 예산 — 제약이 예상과 다르다

### C-1 실측 (`/api/fomo/discovery?country=KR&debug=timings`)

| 호출 | 클라이언트 실측 | 서버 `meta.timings.totalMs` |
|---|---|---|
| 콜드 | **49.0초** | **175ms** |
| 웜 #1 | 4.70초 | 179ms |
| 웜 #2 | 1.59초 | 27ms |

`stages: []` — 완료된 단계가 없고 `pending: [kr-title-cache 2ms]` 뿐이다.

**서버는 175ms 라고 말하는데 사용자는 49초를 기다린다 — 약 280배 차이다.**

#### 이것이 뜻하는 것

1. **요청 시점 계산은 병목이 아니다.** 핸들러는 27~179ms 로 일관되게 빠르다.
   조회 경로의 남은 여유는 **초 단위로 넉넉하다.**
2. **콜드스타트가 예산을 먹는다.** 배포된 람다는 `λ index (10.15MB)` 단일 번들이다
   (`vercel inspect` 실측). 웜업 후 1.59초까지 떨어지는 것이 이를 뒷받침한다.
3. **기존 `stage-timer` 는 이 구간을 못 본다.** C-1 이 "stage-timer 재사용" 을 지시했지만,
   그 계측만으로는 **"남은 여유가 몇 초인가" 에 답할 수 없다.** 175ms 를 보고 여유가 충분하다고
   결론내면 오독이다.

#### 다른 라우트 실측 (참고)

| 라우트 | 클라이언트 실측 |
|---|---|
| `fundamentals/coverage` | **98.3초** (132KB) |
| `card-slots/coverage` | 93.1초 |
| `business-context/coverage` | 93.1초 |
| `risk/coverage` | 4.88초 |
| `quiet-picks` (캐시 히트) | 0.13초 |

### C-2 신규 층 예산 배정 — 결론이 바뀐다

CTX-00 은 "조회 시점 계산 0, 전부 배치 사전계산" 을 요구한다. **그 방향은 여전히 옳다.**
다만 실측이 보여주는 진짜 제약은 다르다:

> **요청당 계산 시간이 아니라 번들 크기(콜드스타트)가 예산의 주 소비자다.**

따라서 CTX-01~04 설계에 조건을 하나 더 건다:

- 배치 잡은 **크론 전용 경로에 격리**한다. 무거운 의존성이 조회 경로 번들에 들어가면
  계산을 0으로 만들어도 **콜드스타트가 늘어 사용자 체감은 나빠진다.**
- 신규 층 도입 전후로 **콜드스타트를 직접 측정**한다(웜업 없는 첫 호출 실측).
- `stage-timer` 만으로 합격 판정하지 않는다.

### 측정 신뢰도 — 정직하게

- 첫 시도에서 **926초**가 나왔다. 직전에 내가 US 무거운 호출(110초)을 했고, 그 경합이
  원인으로 보인다. **깨끗한 측정이 아니라 폐기**하고 위 값으로 재측정했다.
- 위 3개 값도 **단일 리전·단일 라우트·3회** 표본이다. 콜드스타트와 Vercel 큐잉을
  이 측정만으로는 분리하지 못한다 → **그 분해는 미확인.**
