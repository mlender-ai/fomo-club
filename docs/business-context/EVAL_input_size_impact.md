# 입력 크기 영향 평가 (WO-SUB-03.5 PART C-1)

> **질문**: 429 회피로 넣은 `SECTION_PROMPT_CHARS = 3,500` 이 산출물 품질을 바꿨는가?
> **이 평가 없이 3,500자를 확정하면, 인프라 제약이 정한 품질 수준을 제품 사양으로 받아들이는 것이다.**

작성일: 2026-07-25 · 대상: `apps/web/lib/business-context/sec-filing.ts` `SECTION_PROMPT_CHARS`

---

## 1. 먼저 확인된 사실 — 3,500자는 근거의 63~98%를 버린다

A/B 실험 전에, **이미 실행된 골든셋 30종목(`golden30_raw.json`)의 원본 로그**가
입력 축소의 직접 영향을 기록하고 있었다. 청크 예산 초과는 조용히 처리되지 않고 에러로 남는다
(`chunk: 예산 초과로 N개 제외(총 M개)`).

| 종목 | 추출 청크 | LLM 입력 | 버린 청크 | 손실률 |
|---|---|---|---|---|
| Rhinebeck Bancorp | 122 | **2** | 120 | **98%** |
| Adobe | 59 | 3 | 56 | **95%** |
| Micron | 78 | 5 | 73 | **94%** |
| Matson | 83 | 5 | 78 | **94%** |
| CoreWeave | 35 | 2 | 33 | **94%** |
| Byrna Technologies | 53 | 6 | 47 | 89% |
| Shopify | 20 | 3 | 17 | 85% |
| Airbnb | 33 | 5 | 28 | 85% |
| Dell | 36 | 6 | 30 | 83% |
| IBM | 7 | 2 | 5 | 71% |
| Elevance Health | 8 | 3 | 5 | 63% |

**중위 손실률 89%.** 사업 실체 3슬롯은 "공시 원문에 있는 사실만" 쓰도록 설계됐는데,
그 원문의 9할을 버린 상태로 합성과 검증을 돌렸다. 슬롯 채움률이 낮은 것은
모델 성능 문제가 아니라 **근거를 주지 않은 결과**로 보는 것이 타당하다.

## 2. 그런데 골든셋 자체가 무효다 — 429 가 23/30 을 죽였다

같은 로그의 실패 사유 분포:

| 건수 | 사유 |
|---|---|
| **23** | `ai: 합성 호출 실패(429) — 토큰 한도` |
| 4 | `sec: 섹션 추출 실패`(Item 1 헤더/구간 없음) |
| 2 | `slot: 검증 판정 불가 — 폐기` |
| 1 | `slot2: 근거 미지지 — 폐기` |

**30종목 중 23종목은 LLM 을 부르지도 못했다.** 그 결과가 `EVAL_golden30.md` 의
슬롯1 1/30 · 슬롯2 0/30 · 슬롯3 0/30 이다.

→ **이 수치는 "3,500자의 품질"이 아니라 "페이싱 없는 실행의 결과"다.**
3,500자와 24,000자를 비교하려면 **두 조건 모두 429 없이 완주**해야 한다. 페이싱이 선행 조건이다.

## 3. 페이싱 — 추측이 아니라 계산

`DIAG_429_ratelimit.md` 의 실측 한도를 그대로 쓴다.

```
x-ratelimit-limit-tokens = 12,000 / 분  (TPM. 일일 쿼터가 아님)
안전 마진 적용            =  8,400 토큰/분
종목당 콜 수              = 3 (합성 1 + 검증 2 — 검증도 청크를 받는다)
영문 공시 토큰 환산        ≈ 4자/토큰
```

| 입력 크기 | 콜당 입력 토큰(≈) | 종목당 토큰(3콜) | 종목당 소요 | 10종목 | 30종목 |
|---|---|---|---|---|---|
| 3,500자 | ~900 + 프롬프트 ≈ 1,200 | ~3,600 | **26초** | ~4.5분 | ~13분 |
| 24,000자 | ~6,000 + 프롬프트 ≈ 6,300 | ~18,900 | **135초** | ~23분 | ~68분 |

**핵심 제약**: 24,000자에서 종목당 18,900 토큰은 **TPM 12,000 을 한 종목이 초과**한다.
즉 24,000자는 "1분에 1종목"도 불가능하고, 한 종목이 최소 2분 창을 걸쳐야 한다.
불가능하지는 않지만 **무료 티어에서 전량(285종목) 운영은 비현실적**이다(≈11시간).

| 규모 | 3,500자 | 24,000자 |
|---|---|---|
| A/B 실험(10종목 × 2조건) | — | **~28분** (CI 1잡으로 가능) |
| 골든셋 30종목 재실행 | ~13분 | ~68분 |
| 유니버스 전량 285종목 | ~2시간 | **~11시간** |

## 4. 판정 — 지금 확정할 수 있는 것과 못 하는 것

### 확정할 수 있는 것

**3,500자를 "품질 근거로 확정"하는 것은 불가능하다.** §1 이 그 이유다 —
근거의 중위 89%를 버리는 설정을 품질 기준으로 고를 수는 없다. 이 값은
품질 판단의 산물이 아니라 **TPM 회피의 산물**이고, WO 가 지적한 "순서가 거꾸로"인 상태다.

### 확정할 수 없는 것 (실험 필요)

"그럼 24,000자면 슬롯이 채워지는가"는 **아직 데이터가 없다.** §1 은 근거를 버렸다는 사실이고,
근거를 다 주면 슬롯이 채워진다는 증명이 아니다. SEC 섹션 추출 실패(4건)처럼
입력 크기와 무관한 실패도 있다.

**필요한 실험**(WO-SUB-03.5 C-1 명세):

```
대상: SEC 10-K 확보된 US 10종목
조건: SECTION_PROMPT_CHARS = 3,500 / 24,000 각각 1회
페이싱: §3 표 (24,000자 = 종목당 135초 창)
측정: 슬롯 생성 성공률(null 비율) · 검증 패스 통과율 · 인용 청크 다양성
예상 CI 소요: ~28분
```

이 실험은 **GROQ_API_KEY 를 가진 실행 환경**이 필요하다(로컬에 키 없음, 저장소 시크릿에 존재).

### 이 문서가 막고 있는 것

- 3,500자를 "확정"으로 기록하지 않는다 → PART F 체크리스트 "C-1: 입력 크기가 품질 근거로 확정됨" **미충족**
- `EVAL_golden30.md` 의 슬롯 채움률을 품질 지표로 인용하지 않는다 → **B-2 사람 판정도 이 상태로는 무의미**(판정 대상 문장이 1개)
- `PREFLIGHT`/E-3 의 아키타입별 슬롯3 분포도 측정 불가(§5)

## 5. 연쇄 차단 — 이것이 배치의 실제 병목이다

```
TPM 12,000 (외부 제약)
   └ 페이싱 없는 실행 → 429 23/30
   └ 3,500자 축소     → 근거 89% 손실
        ├ 슬롯1 1/30, 슬롯2·3 0/30
        │    ├ B-2 골든셋 사람 판정 → 판정 대상이 1문장 (무의미)
        │    └ E-3 아키타입별 슬롯3 확보율 → 전 유형 0 (분포 없음)
        └ C-1 판정 → 실험 미실행
```

**하나의 원인(페이싱 없는 대량 호출 + 임의 입력 축소)이 세 개의 AC 를 동시에 막고 있다.**
개별 항목을 따로 메우려 하면 같은 벽에 세 번 부딪힌다. 순서는 **페이싱 → C-1 실험 → 골든셋 재실행 → E-3** 이다.

## 6. 사람 결정이 필요한 지점

| 결정 | 선택지 | 비용/영향 |
|---|---|---|
| A/B 실험 실행 방식 | (a) CI 워크플로에서 페이싱 준수 실행 | 무료, ~28분/회 |
| | (b) Groq 유료 티어 | TPM 상향 → 전량 운영 현실화 |
| 입력 크기 확정값 | 실험 결과에 따름 (24,000 / 중간값 / 3,500 유지) | 전량 운영 시간이 2h ↔ 11h 로 갈린다 |

**전량 285종목 운영을 전제하면 24,000자는 무료 티어에서 성립하지 않는다**(11시간).
따라서 이 결정은 "품질 vs 인프라"가 아니라 **"품질 기준을 정하고 그에 맞는 티어를 고르는"** 순서여야 한다.
