### 거래소만 바꾼 이유 — 실측

Hyperliquid `candleSnapshot` 을 직접 찔러봤다.

| 요청 | 결과 |
|---|---|
| 1시간봉, 3년 범위 | **5,003봉** (2026-02-14 ~ 현재 ≈ 7개월) |
| 1시간봉, 2025-01~2025-03 (과거 구간) | **0봉** |
| 1시간봉, 2026-01~2026-02 (더 가까운 과거) | **0봉** |
| 일봉, 5년 범위 | 2,200봉 (2020-09 ~) |

**1시간봉은 최근 5,000봉만 주고 과거 구간은 안 준다.** 3년 = 26,280봉이 물리적으로
불가능하다. 일봉은 충분하지만, 1시간봉이 없으면 `LAB-05` 에서 볼 표본이 얇아진다.

그리고 §0 이 Hyperliquid 를 고른 근거인 **"FCE에 이미 있음" 은 봉 수집이 아니었다.**
FCE `b1c5211` 을 읽어보면:

- `backend/app/onchain/hyperliquid/` — leaderboard · clearinghouseState = **고래 수집기**
- `backend/app/exchange/bitget/` — 봉 · 체결 어댑터

즉 `LAB-00` §5 의 "Hyperliquid 수집 그대로" 는 **PART C(고래)** 를 가리킨다.

### 되돌리려면

## 품질 검사 5종 (PART A-2)

`packages/lab/src/candle-quality.ts` — 순수 함수. 수집기와 백테스트가 **같은 판정**을 쓴다.

| 검사 | 함수 | `ok` 에 반영 |
|---|---|---|
| 봉 개수 | `expectedCandleCount` | 참고값 |
| 구멍 | `findGaps` | **아니오** — 아래 |
| 이상치 | `findOutliers` (기본 ±40%) | 예 |
| 시각(UTC 정렬) | `findMisaligned` | 예 |
| 중복 | `findDuplicates` | 예 |

### 구멍이 `ok` 를 깨지 않는 이유

**구멍은 정상 출력이다.** 거래소가 멈춘 구간은 실제로 봉이 없다. 그걸 실패로 처리하면
수집이 영원히 빨간불이 되거나 — 더 나쁘게 — 누군가 메우려 든다.
구멍은 **세어서 `DataGap` 에 기록**하고, `ok` 는 고칠 수 있는 것만 본다.

보간 함수는 **일부러 만들지 않았다.** 있으면 언젠가 쓰인다.
(`candle-quality.test.ts` 가 `fill`·`interpolate`·`impute` 이름의 export 가 없는지 검사한다.)

`LAB-04` 백테스트는 `isInGap()` 으로 그 구간에서 진입하지 않는다.

## 끊김 처리 (PART B-2)

`packages/lab/src/freshness.ts` — 화면과 페이퍼 실행기가 **같은 함수**를 쓴다.
따로 판단하면 화면은 초록인데 실행기는 멈춰 있는 상태가 생기고, 그러면 왜 안 사는지 아무도 모른다.

- 임계 **3분** (`STALE_AFTER_MS`)
- 한 종목이라도 `stale`·`missing` 이면 **전체 신규 진입 중지**
- 화면: `/data`

> 진입을 막는 쪽이 틀렸을 때의 손해가 작다 — 기회를 놓칠 뿐 **거짓 성과는 안 남는다.**

## 크론 (PART E)

`.github/workflows/lab-collect.yml`

| 잡 | 주기 | 지시서 요구 |
|---|---|---|
| 실시간 시세 | `*/5 * * * *` | 1분 — **못 지킨다**, 아래 |
| 봉 갱신 | `5 * * * *` | 1시간 ✅ |
| 펀딩비 | `10 */8 * * *` | 8시간 ✅ |
| 고래 | `*/15 * * * *` | 5분 — 15분으로 늘림 |
| 과거 백필 | `workflow_dispatch` | 수동 1회 ✅ |

### 1분 주기를 못 지키는 이유

- **Vercel 은 Hobby 플랜**이라 크론이 하루 1회다. 1시간봉 갱신조차 불가능하다.
- **GitHub Actions schedule 최소 간격은 5분**이고 실제로는 더 늦게 뜬다.

그래서 실시간 시세는 5분이다. 진짜 1분 주기는 **상주 워커**가 필요하고,
그건 `LAB-07`(페이퍼 실행기)에서 `apps/api` 워커에 붙인다.

`STALE_AFTER_MS` 를 3분으로 잡은 이유가 이것이다 — 5분 주기에서는 한 번만 늦어도
stale 로 잡히고, **그게 맞다.** 지금 상태를 "정상" 으로 보이게 만들 이유가 없다.

고래를 15분으로 늘린 것은 지갑 30개 스캔에 ~8초가 걸려 5분마다 돌 이유가 없어서다.

### 실패 알림 (PART E-1)

2회 **연속** 실패하면 `LAB_ALERT_WEBHOOK` 으로 보낸다. 웹훅이 없으면 stderr 에 찍는다 —
알림 경로가 없다는 사실 자체가 로그에 남아야 한다.

판정은 **`CollectionRun` 표**에서 한다. 프로세스가 기억하면 배포·재시작마다 초기화돼
매번 실패하는 잡이 영원히 "1회째" 로 보이고, **알림이 안 오는 감시는 없는 감시다.**

## 검증 스크립트

```bash
npm run lab:verify-collect   # 중복·UTC 정렬·구멍 기록·fetchedAt 전진
npm run lab:verify-alert     # 1회는 안 옴 · 2회 연속이면 옴 · 성공 시 리셋
```

두 스크립트가 실제 결함 두 개를 잡았다:

1. **`LatestPrice.fetchedAt` 이 갱신되지 않았다.** `@default(now())` 는 생성 때만 걸리는데
   upsert 의 update 절에서 빠져 있었다. 수집이 멀쩡히 도는데 첫 삽입 시각에 멈춰
   **영원히 stale** 이 되고, 페이퍼 실행기가 진입을 영구히 거부했을 것이다.
2. **"최신 상태" 조기 반환이 품질 검사를 건너뛰었다.** 새 봉이 안 들어오는 동안에는
   기존 구멍이 안 보였다. 받을 게 없을 뿐이지 **볼 게 없는 게 아니다.**
