| 전략당 시작 자본 | **$10,000** |

### 왜 Vercel Cron 이 아닌가

이 계정은 **Vercel Hobby** 라 크론이 하루 1회다. 1시간 주기가 불가능하다.
GitHub Actions 는 schedule 최소 5분이라 1시간은 문제없다.

매시 **15분**에 돈다 — 봉 갱신(매시 5분)이 끝난 뒤다. 같은 분에 돌리면
방금 닫힌 봉이 아직 안 들어와 있어 **한 시간씩 늦게 반영된다.**

## PART A — 실행기를 새로 만들지 않았다

`@fomo/lab` 의 `execute()` — **백테스트가 쓰는 바로 그 함수**를 부른다.
다른 것은 `DataSource` 에 넣는 봉뿐이다:

| | 백테스트 | 페이퍼 |
|---|---|---|
| 봉 | 과거 전부 | **지난 실행 이후 새로 닫힌 봉** |
| 상태 | 메모리 (한 번에 끝까지) | **DB** (`PaperState`) |
| 종료 | 기간 끝 | 없음 |

### 실행기를 이어 돌 수 있게 바꿨다

배치 루프라 재시작이 불가능했다. `execute()` 가 `state` 를 받고 돌려주게 했다 —
현금·보유 포지션·대기 신호·지표 창·고래 이력·마지막 종가·봉 간격.

**같은 엔진이라는 것은 주장이 아니라 검사다**(`engine-resume.test.ts`):

> 시계열을 **한 번에** 돌린 결과와 **조각내 이어 돌린** 결과가 **완전히 같다** —
> 거래의 종목·시각·체결가·수량·청산사유, 그리고 자산곡선의 모든 점까지.

| 검사 | 결과 |
|---|---|
| 60봉씩 나눠 이어 돌리기 | ✅ 동일 |
| **봉 하나씩** 이어 돌리기 | ✅ 동일 |
| 조각마다 **JSON 직렬화·복원**을 끼워서 | ✅ 동일 |
| 되살린 상태의 `Date` 가 진짜 `Date` 인가 | ✅ |
| 망가진 상태는 `null` — 억지로 이어 돌지 않는다 | ✅ |

다르면 페이퍼와 백테스트를 비교할 수 없고, PART G 의 "실매매 전 마지막 관문" 이
통째로 무의미해진다.

### 상태 크기

창을 **500봉**으로 자른다(`DEFAULT_MAX_WINDOW_BARS`). 지금 가장 긴 기간이
`ma_cross` 의 `slow`(60)라 넉넉하다. 실측 상태 크기는 **73 kB**(3종목).

> ⚠️ **500봉보다 긴 기간을 쓰는 정의는 조용히 틀린 값을 받는다.**
> 그런 지표를 넣으려면 이 상수를 같이 올려야 한다.

## PART B — 실행 루프

```
1  잠금을 잡는다          못 잡으면 조용히 끝낸다 (B-2)
2  시세가 stale 인가       그러면 신규 진입 중단 (PART C)
3  전략마다
     상태를 읽고 → 새 봉으로 execute() → 거래·자산 적재 → 상태 저장
4  리스크 한도 확인        넘으면 자동 정지 + 사유 + 알림 (PART E)
```

### B-2. 중복 실행 방지 — 임대(lease) 잠금

`JobLock` 표로 막는다. 프로세스 기억은 재배포마다 초기화되고, 러너가 여러 곳에서
뜰 수 있다(Actions 재시도, 수동 실행). **표가 유일하게 공유되는 자리다.**

**임대 방식인 이유:** 단순 플래그면 **한 번 죽은 실행이 영원히 다음 실행을 막는다.**
크론은 프로세스가 죽었는지 모른다. 만료 시각을 두고, 지나면 뺏는다.

`release()` 는 **내 잠금만** 푼다 — 만료 뒤 남이 잡았을 수 있다.

## PART C — 데이터가 끊겼을 때

| 상황 | 처리 |
|---|---|
| 시세 stale (3분 이상) | **신규 진입 중단.** 보유는 유지, 청산은 그대로 평가 |
| 복구 | 그 구간에 `Equity` 점이 **없다** — 화면이 선을 끊는다 |

**구멍을 보간하지 않는다.** 받은 봉의 시각에만 점을 찍는다.

### `maxPositions: 0` 꼼수를 쓰지 않았다

처음엔 config 의 동시 보유 상한을 0 으로 만들어 막으려 했다. **아무 일도 안 일어났다** —
실행기는 상한을 **정의에서** 읽는다(LAB-04). stale 인데 진입이 되는 것을 실행 로그에서 봤다.

지금은 `blockNewEntries` 라는 명시적 입력이고, 막힌 것은 `blocked.feed_stale` 에 센다.
**보유는 유지되고 청산은 그대로 평가된다** — 끊긴 동안 손절선을 넘었으면 나와야 한다.

## PART D — 체결

**백테스트와 같은 함수**(`fills.ts`)를 쓴다. 다음 봉 시가 진입, 손절가 체결(갭은 시가),
같은 봉 손절+목표는 손절 먼저, 시간 청산은 종가, 펀딩비 8시간.

다른 규칙을 쓰면 두 결과를 비교할 수 없다 — 그래서 **규칙이 담긴 파일이 하나다.**

## PART E — 리스크 한도

| 항목 | 기본 | 환경변수 |
|---|---|---|
| MDD 한도 | **−25%** | `LAB_MDD_LIMIT_PCT` |
| 연속 손실 | **8회** | `LAB_MAX_CONSECUTIVE_LOSSES` |

넘으면 `status=STOPPED` + `stopReason` + **알림**. 이미 멈춘 것은 다시 안 멈춘다 —
알림이 매 시각 울면 아무도 안 본다.

**정지된 전략은 표에 남는다. 지우지 않는다.**

### 새 봉이 없어도 한도는 본다

처음엔 `barCount === 0` 이면 조기 반환했다. 그러면 **시세가 멈춘 동안 한도를 넘긴
전략이 영원히 안 멈춘다.** 봉이 안 와서 안 멈춘다는 것은 이유가 되지 않는다 —
오히려 그때가 더 위험하다. `verify-paper` 가 잡았다.

## PART F — 알림

`LAB_ALERT_WEBHOOK` 으로 POST. 없으면 **stderr 에 찍는다** —
알림 경로가 없다는 사실 자체가 로그에 남아야 한다.

구현은 `scripts/lab/collect/job.ts` **한 곳**이다. 처음엔 수집기와 페이퍼가 각자
갖고 있었는데, 그러면 한쪽만 고쳐지고 다른 쪽은 조용히 안 보내는 상태가 된다.

| 상황 | 구현 |
|---|---|
| 실행 2회 연속 실패 | ✅ `runJob` (`CollectionRun` 표에서 판정) |
| 전략 자동 정지 | ✅ `enforceRiskLimits` |
| 시세 stale 30분 이상 | ⚠️ **미구현** — 현재는 화면(`/data`)과 실행 로그에만 나온다 |
| 신규 진입·청산 | 선택 — 넣지 않았다 |

### F-1. 알림 테스트 — `npm run lab:verify-paper`

> 걸어만 두고 안 오는 경우가 이 프로젝트에서 여러 번 있었다.

로컬 HTTP 서버를 띄워 **실제로 받는지** 본다. 지표를 가짜로 써넣지 않는다 —
실행기가 지표를 다시 재면서 덮어써서 그 검사는 아무것도 검사하지 않게 된다
(실제로 그렇게 짰다가 통과하지 못했다). 대신 **한도를 실측 낙폭 아래로 낮춰**
진짜 경로를 태운다.

> ⚠️ 검증 스크립트에서 자식 프로세스를 `execFileSync` 로 부르면 안 된다.
> 부모의 이벤트 루프가 멈춰서 **웹훅 서버가 자식의 요청에 응답하지 못하고**,
> 자식은 영원히 기다리며 잠금을 쥔 채 멈춘다. 실제로 그렇게 짰다가 걸렸다.
