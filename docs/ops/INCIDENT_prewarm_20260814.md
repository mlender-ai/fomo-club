## 2. 근본 원인 — 시간 제한 초과

두 라우트의 선언과 실패까지 걸린 시간이 정확히 일치한다.

| 라우트 | 선언 | 실패까지 | 로그 |
|---|---|---|---|
| `/api/fomo/discovery` | `export const maxDuration = 60` | **60초** | 06:43:15 → 06:44:15 |
| `/api/fomo/daily-30` | `export const maxDuration = 300` | **약 301초** | 03:06:09 → 03:11:10 |

`discovery` 는 요청 시점에 `buildDiscoveryResponse(...)` 를 돌린다(`unstable_cache` 로 감쌌지만
캐시 미스면 빌드한다). `daily-30` 은 `getCachedDaily30Response()` 안에 "위원회·스냅샷 동시 부재
때 결정론 엔진 직생성까지 허용하는 최후 비상 경로"가 있고 그래서 `maxDuration` 이 300이다.

**즉 오류가 아니라 시간 초과다.** 예외가 던져진 것이 아니라 함수가 제한선에서 잘렸다.

### 현재도 재현된다 (2026-08-14 07:2x UTC 실측)

## C. 근본 원인 — 콜드 빌드가 제한을 넘으면 회복 경로가 없다

```
요청 → 캐시 미스 → 콜드 빌드 시작 → maxDuration 에서 잘림(504)
     → 잘렸으므로 캐시도 못 씀 → 다음 요청도 캐시 미스 → 무한 반복
```

`discovery` 는 `maxDuration=60` / `revalidate=600`, `daily-30` 은 `maxDuration=300` /
`revalidate=300` 이다. **콜드 빌드 비용이 제한선을 넘긴 순간부터 이 시스템은 스스로 캐시를
채울 수 없다.** 재배포 전까지는 따뜻한 캐시가 그 사실을 가리고 있었을 뿐이다.

이 모형이 관측을 전부 설명한다.

- 왜 특정 시각에 시작했나 → 재배포로 캐시가 비었다
- 왜 코드 변경이 없나 → 캐시는 코드가 아니다
- 왜 가끔 성공하나 → 드물게 빌드가 제한 안에 끝나면 캐시가 채워지고 그 뒤 몇 건이 빠르게 성공한다.
  `revalidate` 가 만료되면 다시 콜드 → 실패로 돌아간다(`#1375`·`#1328`·`#1308` 이 그 패턴)
- 왜 스스로 안 낫나 → 회복에 필요한 것(캐시 채우기)이 실패하는 그 동작이다
- 왜 배포할수록 나빠지나 → 배포마다 캐시가 다시 비워진다

**즉 "무엇이 늘었나"의 답은 콜드 빌드 비용이고(임계 초과는 잠복해 있었다), "왜 지금인가"의
답은 재배포다.** 두 개가 같이 있어야 이 사고가 난다.

### 남은 계측 (PHASE 2 — 미완)

단계별 소요(ms)와 상위 3개 병목은 **아직 내지 못했다.** 이 세션에서는 프로덕션 라우트에
계측을 붙일 수 없고(배포 권한), 로컬에서 같은 빌드를 돌릴 수 없다(외부 소스 egress 차단).
대신 DB 쪽만 실측했다:

| 쿼리 | 실측 |
|---|---|
| `FeedContentCache` 접두사 조회(`readFeedContentByPrefix`) | **66.6 ms** · `updatedAt` 인덱스는 타지만 **4,876행을 필터로 버린다**(표가 클수록 증가) |

정확한 병목 순위는 라우트에 타이밍 로그를 심어 한 번 돌려야 나온다. **PHASE 4 구조 결정은
그 수치 없이 하지 않는다** — 이 문서는 그 전까지 결정을 유보한다.

## D. PHASE 3 응급 완화 — 적용함

**빌드 로직은 건드리지 않았다.** "못 만들었을 때 무엇을 주는가"만 바꿨다.

- `apps/web/lib/stale-serve.ts` 신설 — 마감(`withDeadline`) + 마지막 성공분 스냅샷
  (기존 `FeedContentCache` 를 `snapshot:*` 키로 재사용, 새 테이블 없음)
- `discovery` 마감 **25초**(제한 60), `daily-30` 마감 **45초**(제한 300)
- 마감을 넘기면 마지막 성공분을 200 으로 주고 `meta.stale=true` + `savedAt` 을 실어 보낸다 —
  **오래된 것을 최신인 척 주지 않는다**
- 스냅샷이 없으면 빈 200 을 만들지 않고 기존 503 계약을 유지한다
- 빌드를 **취소하지 않는다** — 남은 시간에 끝나면 캐시가 채워져 다음 요청이 빨라진다
  (콜드 데드락에서 빠져나올 유일한 자연 경로)

검증: 테스트 2,010건 통과(+9) · `typecheck:web` · `build:web` 통과.

**주의 — 이것으로 워크플로가 초록이 되더라도 "빌드가 60초 안에 끝났다"는 뜻이 아니다.**
`meta.stale` 이 붙은 200 일 수 있다. 프리웜 성공을 완료 근거로 쓰기 전에 응답의 `stale` 을 본다.
