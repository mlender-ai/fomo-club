## 2. 근본 원인 — 시간 제한 초과

두 라우트의 선언과 실패까지 걸린 시간이 정확히 일치한다.

| 라우트 | 선언 | 실패까지 | 로그 |
|---|---|---|---|
| `/api/fomo/discovery` | `export const maxDuration = 60` | **60초** | 06:43:15 → 06:44:15 |
| `/api/fomo/daily-30` | `export const maxDuration = 300` | **약 301초** | 03:06:09 → 03:11:10 |

`discovery` 는 요청 시점에 `buildDiscoveryResponse(...)` 를 돌린다(`unstable_cache` 로 감쌌지만
캐시 미스면 빌드한다). `daily-30` 은 `getCachedDaily30Response()` 안에 "위원회·스냅샷 동시 부재
때 결정론 엔진 직생성까지 허용하는 최후 비상 경로"가 있고 그래서 `maxDuration` 이 300이다.

**즉 오류가 아니라 시간 초과다.** 예외가 던져진 것이 아니라 함수가 제한선에서 잘렸다.

### 현재도 재현된다 (2026-08-14 07:2x UTC 실측)

| 요청 | 결과 |
|---|---|
| `GET /api/fomo/discovery?country=US` | 60초 무응답 → 타임아웃 |
| `GET /api/fomo/daily-30` | 60초 무응답 → 타임아웃 |
| `GET /api/fomo/quiet-picks` | **200, 약 1초** (`x-vercel-cache: MISS`) |

`quiet-picks` 는 저장된 것을 읽기만 해서 빠르다. 죽은 두 라우트는 **요청 시점에 만든다.**
차이는 부하가 아니라 **구조**다.

## 3. 최초 실패 시점 — 코드 변경이 트리거가 아니다

`us-market-prewarm` 전체 이력 1,389건을 페이지 단위로 훑어 경계를 좁혔다.

| 실행 | 시각(UTC) | 결과 | head_sha |
|---|---|---|---|
| `#743` | 2026-07-27 11:46:51 | success | `a570c08` |
| **`#744`** | **2026-07-27 13:42:34** | **failure (첫 실패)** | **`a570c08`** |

**직전 성공과 첫 실패의 커밋이 같다.** 그 사이 main 에 머지된 것이 없다 —
따라서 이 경계에서 **배포된 코드 변경이 원인일 수 없다.**

간헐 실패로 시작해 전면 실패로 굳었다. **이것은 어떤 순간에 깨진 것이 아니라 임계선을
서서히 넘은 것이다** — 이 곡선이 그 판단의 근거다(추론임을 밝힌다. 무엇이 빌드를 무겁게
만들었는지는 별도 계측이 필요하고, PART 2에서 라우트 자체를 고치면 원인 지표도 같이 남는다).

### 남아 있는 성공은 무엇인가

`us-market-prewarm` 의 스텝 ③은 `if: steps.slot.outputs.slot == '1'` 이다. 슬롯은 실행 시각의
분(`date -u +%M`)이 10의 배수면 0이다. **슬롯 0으로 뜬 실행은 ③을 건너뛰므로 성공한다.**
`#1375`(21:40)·`#1368`(18:30)·`#1364`(16:30) 가 그것이다. 슬롯 1인데 성공한 것도 드물게 있다
(`#1328`·`#1308`) — 그때는 빌드가 60초 안에 끝났다는 뜻이다.

`feed-content` 는 슬롯별로 갈린다.

| 슬롯 | 크론(UTC) | 최근 결과 |
|---|---|---|
| index / morning / daily30 | 20:00 · 20:30 · 21:30 | **성공** (`#204~#206`, 08-13 20:36~22:12) |
| pulse / close | 00:30~05:30 · 07:10 | **실패** (`#207~#209`, 08-14 03:06~06:52) |

| 후보 | 판정 | 근거 |

| 타임아웃 | **확정(같은 사실의 다른 이름)** | `maxDuration` 선언값과 실패 시각 일치 |

| 시크릿 부재 | **부수 발견** | 아래 |

### 부수 발견 — `CRON_SECRET` 이 주입되지 않는다

`#1389` 로그의 환경 덤프:

```
env:
  SLOT: 1
  CRON_SECRET:        ← 빈 값
```

워크플로는 빈 값이면 인증 헤더 없이 호출하고, 백엔드 `isAuthorized()` 는 서버에 시크릿이
설정돼 있지 않으면 통과시킨다. 그래서 **지금 크론 라우트는 사실상 무인증 공개 상태**다.
이번 실패의 원인은 아니지만 별건으로 등재한다.

## 5. 영향 범위 — 페이로드는 며칠치 안 갱신됐나

**"페이로드가 안 구워졌다"는 이번 건에서 성립하지 않는다.** 실패한 것은 굽기가 아니라 조회다.

| 페이로드 | 굽는 주체 | 최신 상태 |
|---|---|---|
| 조용한 픽 | Vercel Cron `25 21 * * *` (워크플로 아님) | `asOf 2026-08-13T21:36:11Z` — **정상**. 다음 굽기는 오늘 21:25 UTC |
| US 시세/스파크라인 | `us-market-prewarm` 스텝 ② | **정상** — `#1389`가 263행 기록 |
| feed-content index/morning/daily30 | `feed-content` | **정상** — 08-13 20:36~22:12 성공 |
| feed-content pulse/close | `feed-content` | **실패 지속** — 장중 급변 감지·국장 마감 브리핑이 안 돎 |

즉 실제 사용자 영향은 **① pulse/close 콘텐츠 부재**와 **② 발견 덱 조회 자체가 60초 넘어 실패**다.
②는 워크플로만의 문제가 아니라 **앱에서 발견 API를 호출하는 사용자도 같은 504를 받는다** —
이것이 이번 조사에서 가장 무거운 사실이다.

## 7. 조치 (PART 2 이후 — 미착수)

1. **`/api/fomo/discovery`·`/api/fomo/daily-30` 을 조회 시점 빌드에서 떼어낸다.** 저장된 것을
   읽게 하고, 빌드는 크론이 한다. `quiet-picks` 가 이미 그 구조이고 1초에 응답한다.
2. 워크플로의 검증 스텝에 `--max-time` 을 주고, 실패 시 무엇이 몇 초에 끊겼는지 남긴다.
3. 스케줄 워크플로 연속 실패 감지(PART 3) — 이 사건은 18일간 아무도 못 봤다.
4. `CRON_SECRET` 주입 여부 결정(§4 부수 발견).

**1번을 하기 전에는 재실행을 반복하지 않는다.** 지금 재실행하면 같은 504가 난다.
